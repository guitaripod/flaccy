# CLAUDE.md

## Cross-client parity (read first)

**Flaccy is the product, not any single app.** It ships as four clients — iOS (`flaccy/`), macOS (`flaccyMac/`), watchOS (`flaccyWatch Watch App/`), and Linux (`linux/`, Rust + GTK) — and they must be **as great and in-sync as possible**. A feature, fix, or behavior that lands on one client is incomplete until it lands on the others (or the gap is deliberately recorded).

- **When you change behavior on one client, port it to all the others in the same unit of work.** If a client genuinely can't get it (platform limitation) or you can't verify it (e.g. no Xcode on this Linux box), say so explicitly and leave a tracked note — never silently ship a one-client fix.
- **Share logic, don't fork it.** The three Apple clients share `FlaccyCore` (pure Swift/Foundation where possible) — put cross-client logic there and route every call site through it instead of copy-pasting sorts/parsers. The Linux client is a separate Rust codebase, so it mirrors the same behavior in Rust; keep the two implementations semantically identical and cover both with tests.
- **Parity applies to behavior AND experience.** Ordering, grouping, metadata handling, naming, empty states, and the overall feel should match across clients, adapted to each platform's idioms (UIKit / AppKit / SwiftUI / GTK) — not reinvented.
- Pure shared logic (e.g. `FlaccyCore` ordering/parsing) can be compiled and unit-tested standalone on this Linux box via swiftly even when the full app can't build here — use that to verify cross-client logic before claiming it works.

### Recorded parity gaps

- **Vim-style list navigation (`j`/`k` scroll, `gg` top, `Shift+G` bottom) is Linux-only** (`linux/src/ui/window.rs` capture-phase keyboard handler + the `Ui` scroller registry). Deliberate platform idiom: AppKit lists already have native keyboard scrolling on macOS, and iOS navigates by touch with the A-Z section index. Search opens via Ctrl+F on Linux and Cmd+F on macOS only — there is deliberately no type-to-search. The cross-client *behavior* — changing any sort snaps the list back to the top — is implemented on all three clients.
- **Linux 1.8.0 was mostly parity catch-up** — the Apple clients already had a Now Playing volume slider, go-to-artist/album from the player, context-menu Go to Album / Go to Artist, Show in Finder, and queue-row menus; Linux now matches (`Show in Files` via the portal, label links via `controls::attach_label_nav`). Three things landed Linux-first and have since been ported: the persisted swap of which sides Lyrics/Up Next occupy (`np_swap_sides` → `NowPlayingLayout.swapSides`, with a header button that appears once both panels are open; iOS's player is single-column, N/A), the artist context menu's Play Next / Add to Queue, and Stats top-artists click-through (macOS already had that one — `ChartsViewController.renderArtists` sets `row.clickAction`).
- **Library-load progress is one shared model with four platform-shaped surfaces.** The phases, weights, fraction and tallies live in `FlaccyCore.LibraryLoadProgress` (mirrored in Rust as `linux/shared/src/load_progress.rs` — same phase order, same weights, both covered by tests), and the wording lives in `LibraryLoadPhaseCopy`. What differs is deliberate: iPhone shows a full-screen setup view with a determinate ring while there is no library to browse and a slim banner once there is; macOS never takes the window over — it floats a status strip (the Mac already has an onboarding panel for the empty case); Linux names the phase and counts in its header scan bar and turns the empty albums page into the same live report; watchOS reports the phases on a wrist-sized ring. Every client reads its database before touching the disk, so a relaunch shows the library immediately and the scan is progress rather than a wall.
- **Metadata enrichment is one shared, versioned, resumable job — not a step in the load bar.** The idempotence predicate, the 1 d → 7 d → 30 d → terminal backoff ladder, the three scopes and the SQL seeds live in `FlaccyCore/Sources/FlaccyCore/Library/EnrichmentJob.swift` and are mirrored in Rust as `linux/shared/src/enrichment_job.rs` (with `LibraryDebut.swift` ⇄ `library_debut.rs` and `LibrarySurface.swift` ⇄ `library_surface.rs`); `bash scripts/test-shared.sh` proves both sides, and `cargo test -p flaccy-shared --manifest-path linux/Cargo.toml` runs on the Mac that also builds the Apple clients while the `flaccy` crate does not (`pkg-config` finds no `gstreamer-1.0` there) — which is the entire reason `linux/shared/` was extracted from `linux/src/`. Two invariants hold everywhere: the load bar carries **bounded disk work only** and therefore always reaches a real 100% (`publishLibraryTallies` closes `.buildingAlbums` out on a real total; it used to stall at 92.5% and vanish), and the job is reported as a **countdown** — "12 left" — never a percentage and never a bar, which is why `EnrichmentJobProgress` deliberately carries no fraction property: unbounded network work has no honest denominator. All three scopes including `aiBatch` exist in both models — do not "simplify" the Rust one by dropping it — but **Linux never calls Groq** (GPL client, no purchase, no proxy key), so `Scope::AiBatch` always reports zero there (`linux/src/db.rs`) and the AI copy constants in `linux/shared/src/library_debut.rs` are defined-but-unused on purpose, keeping the Rust deck word-for-word identical to the Apple `LibraryDebutCopy`. Two divergences are deliberate: number grouping (locale-aware `NumberFormatter` in `flaccy/LibraryLoadPhaseCopy.swift`, U+202F via `group_digits` in Rust), and the order of the key normalizer's steps — compose → trim → lower in Swift, trim → lower → compose in Rust — which agree over the Latin ranges real music tags carry and are pinned by the cross-language key tests.
- **The enrichment key must be normalized identically in SQL and in code, and that is not free.** SQLite's own `lower()` folds ASCII only and its `trim()` strips spaces alone, so every queue, seed and orphan-sweep statement calls a registered scalar function — `flaccy_norm`, named by `EnrichmentKey.sqlFunctionName` / `job::NORM_FN` — that runs the exact normalizer the app uses: GRDB `Configuration.prepareDatabase` in `DatabaseManager.openDatabase(at:)` so the v10 seeds get it too, `create_scalar_function` in `Db::open` before the migration block. Normalize each half of a composite key separately, never the concatenation. Getting this wrong does not error: "Ágætis byrjun" is keyed one way by the app and another by the SQL, so the album reports due forever *and* the orphan sweep deletes its state on every scan — a permanent, silent, full re-enrichment of every album with an accented character. `flaccyTests/DatabaseManagerEnrichmentTests.swift` (target created by `scripts/add_unit_test_target.rb`, registered in `flaccy.xctestplan`) is the Apple half of that proof: it runs the four hand-written queue literals against `EnrichmentPolicy.isDue` over every status/version/fields/eligibility combination, and it is the only place the `aiBatch` scope can ever be covered, since Rust has no such scope to mirror.
- **`LibrarySurface` / `LibrarySurfaceRouter` is the single source of truth for launch chrome.** One shared router answers `.none` / `.ambient` / `.debut`, and a client may render what it asked for and nothing else: the derived `showsFullScreen` / `showsBanner` / `hasLibrary` booleans were deleted outright (`hasLibrary` survives only as an *input* to `route(...)`), so no derivation path is left to reinstate the bug the user actually reported — a debut ring painted once at 1%, then crossfaded away frozen, because two booleans derived at Combine delivery time disagreed between snapshots.
- **The Debut is once per library on all four clients, gated on a single `libraryDebut` row, in four platform shapes.** iPhone plays the three acts full-screen; **the Mac's lives inside the existing glass onboarding panel** (`flaccyMac/UI/Onboarding/MacLibraryDebutView.swift`, content dimmed behind it) because the Mac never takes the window over; Linux ends on an `adw::Dialog` summary (`linux/src/ui/debut.rs`); watchOS shows a wrist-sized card (`WatchDebutSummaryView`). The gate is per *library*, not per person — a reinstall or a cleared Application Support gets the showpiece again, correctly. Act I's mosaic is fuelled by embedded artwork hoisted as the tag pass commits each batch (`Library.albumCoversHoisted`, consumed by both the iOS controller and `MacLibraryDebutView`), so it fills offline and for free instead of waiting for the album build. **watchOS renders the PHONE's job over WatchConnectivity and makes no network calls of its own** (`EnrichmentStatusRow`). Note the mechanical trap behind the watch's copy: `scripts/add_watch_target.rb` globs only the watch folder, so `flaccy/LibraryLoadPhaseCopy.swift`, `EnrichmentJobCopy.swift` and `LibraryDebutCopy.swift` are named explicitly in `SHARED_SOURCES` — that glob is exactly why the watch used to carry hand-copied wording describing phases that no longer existed. Both target scripts need the `xcodeproj` gem (`gem install xcodeproj --user-install`).
- **The job's circuit breaker and its re-queue trigger differ by platform on purpose, and both are load-bearing.** `EnrichmentPolicy.transportFailuresBeforeWaiting` (5, mirrored as `job::TRANSPORT_FAILURES_BEFORE_WAITING` and pinned by `policy_constants_match_the_apple_clients`) is what stops a captive portal — which reports a perfectly satisfied route while answering every request with a login page — from burning a whole backlog: after five consecutive transport verdicts the pass parks. **Apple counts per scope** (`consecutiveTransportFailures` is reset at each `drain(scope:)`) and resumes on a genuinely *new* satisfied path, tracked by a generation counter so a path landing between the decision to wait and the parking cannot be lost; **Linux counts process-wide** across its three workers (`Gates::note_verdict`) and parks them on `network_suspect`, a flag deliberately separate from GIO's `network_available` because GIO calls a captive portal reachable. Because nothing durable is written for a transport failure, parking costs the queue nothing — but a park with no way out would be worse than the bug, so Linux clears the flag on a route change, on a 60 s timer armed from `drain_completions`, and on every `schedule_background_pass`, which is what keeps Try Again from being a no-op. The re-queue trigger also differs: the Apple clients call `EnrichmentCoordinator.resume()` at the tail of `doReload()`, while Linux fires `enrichment::request_background_pass` on the scan-settled edge (both arms of `rescan()`'s consumer) because its scan thread commits tracks the reload has not read yet; and Linux derives job *activity* from requests in flight (`enrich_in_flight`) rather than from the due count, since a hundred albums a transport failure left pending are still due while nothing is being worked on.
- **The Debut's second act must never be skipped, and the shared director is where that is enforced.** `LibraryDebutDirector.advance(…, jobHeardFrom:)` reads a drained queue as "the job is over" — but the job's snapshot starts life `.idle` with nothing remaining, which reads as drained, so an act evaluated before the coordinator has published would jump straight from the load bar to the summary card and the AI showcase (the one thing justifying the unlock) would never render. Both Apple clients pass `heardFromJob || elapsedInFinishing >= 2` (`LibraryViewModel.jobHasSpoken`, `ContentRouter.jobHasSpoken`), the coordinator publishes its true `remaining` *before* the expensive page read so a 3 000-album library reports in time, and Linux does the same job with `Stage::ready_to_advance`'s `job_primed`. The 90 s curtain remains the hard ceiling on every client: a job that never reports can delay the card, never hold it.
- **Two root-cause bugs this feature killed, so nobody reintroduces them.** `saveAlbumCoverArtIfMissing` had zero callers, so `albumInfo.coverArtData` was always NULL, the "this album already has a cover" skip never fired, and every album re-enriched on a 24 h TTL forever; `insertTracks` now routes every insert through `hoistingCoverArt`, which is also what feeds the mosaic and what migration v10 backfills. On Linux, `apply_album_enrichment` stamped `lastFetched` unconditionally, so a single offline launch poisoned every queued album for 30 days; scheduling now lives only in `enrichmentState`, `lastFetched` is never stamped, and `apply_album_enrichment_no_longer_stamps_last_fetched` guards it. **`linux/src/` is UNVERIFIED for this change** — the crate has not been compiled since it landed, because it cannot build on the Mac; run it on the arch box before it ships.
- **Linux 1.9.0 now-playing row indicator matches iOS, and goes further.** iOS already draws three animated equalizer bars in place of the track number with an accent-tinted title (`flaccy/AlbumDetailViewController.swift` `AlbumTrackCell`/`NowPlayingBarsView`); Linux mirrors it exactly (`controls::track_index_cell` + `attach_now_playing_row`, Cairo-drawn bars — GTK only re-measures CSS-animated `min-height` sporadically, so the stylesheet version barely moved). Linux applies it in album detail, playlist detail, the songs table and the queue panel. The Mac's playlist detail now observes `trackDidChange` and repaints its title column like the songs table does, so playlist rows light up there too. iOS now lights up playlist detail too (`PlaylistTrackCell` carries the shared `NowPlayingBarsView`); its songs *collection* view is the last surface without it, and the grid/compact cells would need a different treatment than a leading bars slot.
- **Now Playing panel state persists on Linux and macOS** (`np_show_lyrics` / `np_show_queue` / `np_swap_sides` in `linux/src/config.rs`, `NowPlayingLayout` in `flaccyMac/UI/NowPlaying/`). iOS's player is a single column with no side panels, so there is nothing to remember. Deliberately *not* persisted anywhere: the queue contents and playback position — that is session restore, a separate feature, not view configuration.
- **Lyrics resolution is the same on all three clients** (`linux/src/lyrics.rs`, `flaccy/LyricsService.swift` — the latter compiles into both Apple targets): cache → the user's own `.lrc`/`.elrc` sidecar or an embedded lyrics tag (enhanced word tags stripped) → lrclib, and on a 404 retry without the album name before ranking `/api/search` results locally with the same weights (title .35 / artist .30 / duration .25 / has-synced .06 / album .04, hard-rejecting >15 s duration drift, accepting at 0.80). Misses cache for 30 days and are distinguished from network failures, which offer Retry instead of a permanent blank. Two deliberate differences: Linux reads tags with lofty while the Apple side asks AVFoundation, which surfaces fewer Vorbis-comment keys — the sidecar path is the reliable one there; and lyrics text size is user-configurable on Linux only (`lyrics_font_size`), because the Apple clients scale with Dynamic Type instead.
- **Synced-lyrics timing and scroll match on all three clients.** All three re-evaluate the active line every frame with a small lead (`LYRIC_LEAD` / `lyricLead`, ~0.22 s) covering sink latency and the emphasis fade, and auto-scroll with a critically damped spring integrated per frame, anchored at 0.42 of the viewport, retargeting without losing velocity; end padding is sized from the viewport so the first and last lines can reach the anchor. Linux uses the widget frame clock (`FrameDriver`); macOS uses a 60 Hz `.common`-mode run-loop ticker **on purpose** — AppKit pauses a view's `CADisplayLink` whenever the app isn't frontmost, which is most of a music player's life, and the lyrics simply stop (verified: `wanted=true` every tick, zero frames). iOS uses a real `CADisplayLink` (UIKit does not pause it for a backgrounded-but-visible app the way AppKit does), integrating the same spring over `tableView.contentOffset`.
- **Queue panels pin NOW PLAYING to the top of the viewport, history one scroll above** — on all three clients now. Linux (`Pinner` in `linux/src/ui/queue_panel.rs`) keeps the goal as state across rebuilds, re-derives it from live geometry every frame, and grows a trailing spacer row; macOS (`pinNowPlayingToTop` in `flaccyMac/UI/NowPlaying/QueuePanelViewController.swift`) pins the Now Playing heading row and uses `scrollView.contentInsets.bottom` as the equivalent of that spacer, retried from `viewDidLayout` until there is a viewport to pin against; iOS does `scrollToRow(at: .top)`. On every client a rebuild that isn't a track change keeps the reader's scroll position instead of pinning.
- **Verifying the Mac client from the Linux box:** `scripts/build-mac.sh [ios|mac|watch]` rsyncs and builds over Tailscale, and the DEBUG-only `flaccyMac/App/DebugDrive.swift` self-captures window PNGs (`--shot-queue`, `--shot-nowplaying-lyrics`, `--shot-queue-deep`, `--deep`, `--deep-last`, …) into the app's temp dir. Launch the binary directly (`Flaccy.app/Contents/MacOS/Flaccy <flags> &`) — `open --args` drops the flags — and note that `--shot-queue`'s inspector route relies on `NSSplitViewItem.animator()`, which never expands when the app is driven headlessly; the Now Playing shots exercise the same panels and do work.
- **Every artist page leads with Popular.** `artist.getTopTracks` narrowed to what the library owns, in Last.fm's order — `fill_popular` in `linux/src/ui/artists.rs` (top 5, rows carrying the now-playing indicator and the track context menu) alongside the Apple clients' existing sections. Nothing renders when none of the artist's popular songs are owned.
- **Music video mode is Linux-only, for the same reason Downloads is** (`linux/src/musicvideo/`, `linux/src/ui/video_view.rs`). The Now Playing lens swaps the hero artwork for the song's music video: a second `playbin3` decodes picture only into a `gtk4paintablesink` paintable while the lossless file on disk stays the clock. Four pieces worth knowing before touching it. (1) **The pipeline flag `video+download` is load-bearing** — streamed straight from HTTP, playbin refuses every seek, and seeking is how the picture is held to the audio; with download buffering the measured drift goes from a permanent five seconds to ≤60 ms. (2) **Format selection must demand `protocol^=http`** — YouTube also offers the same video as HLS, whose segments need a transport-stream demuxer many installs lack; a decoder failure retries once in H.264 (`stream::format_selector`). (3) **The video is not the album master** — runtime is bounded by *ratio* (0.5–1.9×), never by seconds, because official videos are routinely a minute shorter than the album cut; the offset between the two timelines is measured by cross-correlating spectral-flux onset envelopes of both recordings (`musicvideo::align`, pure Rust FFT, no new system dep) and cached forever. (4) **Picking the right result is scored, not guessed** — uploader identity and view count carry it, because every re-upload copies the title; a local Ollama model only breaks ties the scorer calls close, and its verdict is blended rather than obeyed (`score.rs`, `llm.rs`). Not portable to the Apple clients: it shells out to `yt-dlp`, and App Review Guideline 5.2.3 rules out an App Store build that streams YouTube. If it ever comes to the Mac outside the App Store, `FlaccyCore` should get the scorer and the aligner; the pipeline would be `AVPlayer` with the same governor.
- **Downloads (paste a YouTube/etc. link → best audio → library) is Linux-only** (`linux/src/downloads.rs`, `linux/src/ui/downloads.rs`, shipped 1.6.0). Deliberate: it shells out to `yt-dlp`/`ffmpeg`, which iOS/watchOS cannot run, and an App Store build that rips YouTube audio would violate App Review Guideline 5.2.3 regardless of implementation. If this ever comes to the Apple side, it needs a different design (e.g. user-provided files via the existing document-picker import, or a Mac-only build outside the App Store) — do not port the yt-dlp approach.

## Key Technical Details
- **Database**: GRDB (SQLite) for library persistence, metadata, scrobble queue
- **AI**: Groq (llama-3.3-70b) via the flaccy-api proxy Worker (guitaripod/flaccy-api, flaccy-api.midgarcorp.cc) for music identification and metadata cleanup — no API key in the app
- **Scrobbling**: Last.fm API with ASWebAuthenticationSession OAuth
- **Audio**: AVQueuePlayer for gapless FLAC playback
- **UI Pattern**: Fully programmatic UIKit (no storyboards/XIBs)
- **Architecture**: MVVM pattern throughout
- **Target**: iOS 18, iPhone only
- **Scene Management**: Root view controller set programmatically in `SceneDelegate.scene(_:willConnectTo:options:)`

## Development Patterns
- Follow the existing programmatic UI approach - no Interface Builder
- Use UIStackView's heavily to simplify the layout code. UIStackView's are very configurable and performant.
- Always use the latest UIKit APIs like diffable datasource
- Use MVVM architecture for all screens
- UIKit only - No SwiftUI
- Keep view controllers focused - delegate business logic to view models. Use latest UIKit API like diffable datasource etc.
- Prefer Protocol-Oriented-Programming over Object-Oriented-Programming
- **Logging**: Use `AppLogger` for all logging - never use `print()` statements. AppLogger provides structured logging with categories (auth, database, content, sync, learning, gamification, purchases, ui, viewModel, mlx, performance, general)
- **Code Style**: Never use comments or MARK statements - code should be self-documenting through clear naming and structure
