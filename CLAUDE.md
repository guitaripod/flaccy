# CLAUDE.md

## Cross-client parity (read first)

**Flaccy is the product, not any single app.** It ships as four clients — iOS (`flaccy/`), macOS (`flaccyMac/`), watchOS (`flaccyWatch Watch App/`), and Linux (`linux/`, Rust + GTK) — and they must be **as great and in-sync as possible**. A feature, fix, or behavior that lands on one client is incomplete until it lands on the others (or the gap is deliberately recorded).

- **When you change behavior on one client, port it to all the others in the same unit of work.** If a client genuinely can't get it (platform limitation) or you can't verify it (e.g. no Xcode on this Linux box), say so explicitly and leave a tracked note — never silently ship a one-client fix.
- **Share logic, don't fork it.** The three Apple clients share `FlaccyCore` (pure Swift/Foundation where possible) — put cross-client logic there and route every call site through it instead of copy-pasting sorts/parsers. The Linux client is a separate Rust codebase, so it mirrors the same behavior in Rust; keep the two implementations semantically identical and cover both with tests.
- **Parity applies to behavior AND experience.** Ordering, grouping, metadata handling, naming, empty states, and the overall feel should match across clients, adapted to each platform's idioms (UIKit / AppKit / SwiftUI / GTK) — not reinvented.
- Pure shared logic (e.g. `FlaccyCore` ordering/parsing) can be compiled and unit-tested standalone on this Linux box via swiftly even when the full app can't build here — use that to verify cross-client logic before claiming it works.

### Recorded parity gaps

- **Vim-style list navigation (`j`/`k` scroll, `gg` top, `Shift+G` bottom) is Linux-only** (`linux/src/ui/window.rs` capture-phase keyboard handler + the `Ui` scroller registry). Deliberate platform idiom: AppKit lists already have native keyboard scrolling on macOS, and iOS navigates by touch with the A-Z section index. Search opens via Ctrl+F on Linux and Cmd+F on macOS only — there is deliberately no type-to-search. The cross-client *behavior* — changing any sort snaps the list back to the top — is implemented on all three clients.
- **Linux 1.8.0 was mostly parity catch-up** — the Apple clients already had a Now Playing volume slider, go-to-artist/album from the player, context-menu Go to Album / Go to Artist, Show in Finder, and queue-row menus; Linux now matches (`Show in Files` via the portal, label links via `controls::attach_label_nav`). Three things landed Linux-first and have since been ported: the persisted swap of which sides Lyrics/Up Next occupy (`np_swap_sides` → `NowPlayingLayout.swapSides`, with a header button that appears once both panels are open; iOS's player is single-column, N/A), the artist context menu's Play Next / Add to Queue, and Stats top-artists click-through (macOS already had that one — `ChartsViewController.renderArtists` sets `row.clickAction`).
- **The Stats top lists are playable on every client that has Stats (watchOS has none).** Each list header carries Play and Shuffle for everything the library owns behind that chart, in rank order — Top Tracks the songs, Top Albums each release whole, Top Artists everything by each artist (credited albums plus performances, the `ownedTracks()` rule) — with entries the library lacks skipped and the buttons hidden when nothing resolves. A row tap/click plays: a song within the whole Top Tracks queue, an album, an artist as a station (the iPhone's long-standing tap behaviour, now the rule). That **replaces the Mac and Linux row click-through to the artist/album page**, which moved to the row's context menu (`View Artist` / `Go to Artist`, plus the usual track and album menus) because a row cannot both play and navigate on the same click. Resolution is `RecapLibraryIndex.queue(forTracks:albums:artists:)` ⇄ `ChartIndex` in `linux/src/chart_queue.rs` (case-, diacritic- and punctuation-insensitive; unit-tested). Linux's local charts store `"Title — Artist"` strings, so the index tries every ` — ` split until one resolves, because titles and artists can both contain the separator. `Library::artist_tracks` is now the one artist-queue rule behind `Core::artist_tracks`, and `AppCore::play_list` is the one seeded-shuffle start behind album, artist and chart playback.
- **Library-load progress is one shared model with four platform-shaped surfaces.** The phases, weights, fraction and tallies live in `FlaccyCore.LibraryLoadProgress` (mirrored in Rust as `linux/shared/src/load_progress.rs` — same phase order, same weights, both covered by tests), and the wording lives in `LibraryLoadPhaseCopy`. What differs is deliberate: iPhone shows a full-screen setup view with a determinate ring while there is no library to browse and a slim banner once there is; macOS never takes the window over — it floats a status strip (the Mac already has an onboarding panel for the empty case); Linux names the phase and counts in its header scan bar and turns the empty albums page into the same live report; watchOS reports the phases on a wrist-sized ring. Every client reads its database before touching the disk, so a relaunch shows the library immediately and the scan is progress rather than a wall.
- **Metadata enrichment is one shared, versioned, resumable job — not a step in the load bar.** The idempotence predicate, the 1 d → 7 d → 30 d → terminal backoff ladder, the three scopes and the SQL seeds live in `FlaccyCore/Sources/FlaccyCore/Library/EnrichmentJob.swift` and are mirrored in Rust as `linux/shared/src/enrichment_job.rs` (with `LibraryDebut.swift` ⇄ `library_debut.rs` and `LibrarySurface.swift` ⇄ `library_surface.rs`); `bash scripts/test-shared.sh` proves both sides, and `cargo test -p flaccy-shared --manifest-path linux/Cargo.toml` runs on the Mac that also builds the Apple clients while the `flaccy` crate does not (`pkg-config` finds no `gstreamer-1.0` there) — which is the entire reason `linux/shared/` was extracted from `linux/src/`. Two invariants hold everywhere: the load bar carries **bounded disk work only** and therefore always reaches a real 100% (`publishLibraryTallies` closes `.buildingAlbums` out on a real total; it used to stall at 92.5% and vanish), and the job is reported as a **countdown** — "12 left" — never a percentage and never a bar, which is why `EnrichmentJobProgress` deliberately carries no fraction property: unbounded network work has no honest denominator. All three scopes including `aiBatch` exist in both models — do not "simplify" the Rust one by dropping it — but **Linux never calls Groq** (GPL client, no purchase, no proxy key), so `Scope::AiBatch` always reports zero there (`linux/src/db.rs`) and the AI copy constants in `linux/shared/src/library_debut.rs` are defined-but-unused on purpose, keeping the Rust deck word-for-word identical to the Apple `LibraryDebutCopy`. Two divergences are deliberate: number grouping (locale-aware `NumberFormatter` in `flaccy/LibraryLoadPhaseCopy.swift`, U+202F via `group_digits` in Rust), and the order of the key normalizer's steps — compose → trim → lower in Swift, trim → lower → compose in Rust — which agree over the Latin ranges real music tags carry and are pinned by the cross-language key tests.
- **The enrichment key must be normalized identically in SQL and in code, and that is not free.** SQLite's own `lower()` folds ASCII only and its `trim()` strips spaces alone, so every queue, seed and orphan-sweep statement calls a registered scalar function — `flaccy_norm`, named by `EnrichmentKey.sqlFunctionName` / `job::NORM_FN` — that runs the exact normalizer the app uses: GRDB `Configuration.prepareDatabase` in `DatabaseManager.openDatabase(at:)` so the v10 seeds get it too, `create_scalar_function` in `Db::open` before the migration block. Normalize each half of a composite key separately, never the concatenation. Getting this wrong does not error: "Ágætis byrjun" is keyed one way by the app and another by the SQL, so the album reports due forever *and* the orphan sweep deletes its state on every scan — a permanent, silent, full re-enrichment of every album with an accented character. `flaccyTests/DatabaseManagerEnrichmentTests.swift` (the `flaccyTests` target in `project.yml`, run by the `flaccy` scheme beside `FlaccyCoreTests`) is the Apple half of that proof: it runs the four hand-written queue literals against `EnrichmentPolicy.isDue` over every status/version/fields/eligibility combination, and it is the only place the `aiBatch` scope can ever be covered, since Rust has no such scope to mirror.
- **`LibrarySurface` / `LibrarySurfaceRouter` is the single source of truth for launch chrome.** One shared router answers `.none` / `.ambient` / `.debut`, and a client may render what it asked for and nothing else: the derived `showsFullScreen` / `showsBanner` / `hasLibrary` booleans were deleted outright (`hasLibrary` survives only as an *input* to `route(...)`), so no derivation path is left to reinstate the bug the user actually reported — a debut ring painted once at 1%, then crossfaded away frozen, because two booleans derived at Combine delivery time disagreed between snapshots.
- **The Debut is once per library on all four clients, gated on a single `libraryDebut` row, in four platform shapes.** iPhone plays the three acts full-screen; **the Mac's lives inside the existing glass onboarding panel** (`flaccyMac/UI/Onboarding/MacLibraryDebutView.swift`, content dimmed behind it) because the Mac never takes the window over; Linux ends on an `adw::Dialog` summary (`linux/src/ui/debut.rs`); watchOS shows a wrist-sized card (`WatchDebutSummaryView`). The gate is per *library*, not per person — a reinstall or a cleared Application Support gets the showpiece again, correctly. Act I's mosaic is fuelled by embedded artwork hoisted as the tag pass commits each batch (`Library.albumCoversHoisted`, consumed by both the iOS controller and `MacLibraryDebutView`), so it fills offline and for free instead of waiting for the album build. **watchOS renders the PHONE's job over WatchConnectivity and makes no network calls of its own** (`EnrichmentStatusRow`). Note the mechanical trap behind the watch's copy: the watch target compiles its own folder only, so `flaccy/LibraryLoadPhaseCopy.swift`, `EnrichmentJobCopy.swift` and `LibraryDebutCopy.swift` are named explicitly under `sources` of the `flaccyWatch Watch App` target in `project.yml` — leaving them out is exactly why the watch used to carry hand-copied wording describing phases that no longer existed.
- **The job's circuit breaker and its re-queue trigger differ by platform on purpose, and both are load-bearing.** `EnrichmentPolicy.transportFailuresBeforeWaiting` (5, mirrored as `job::TRANSPORT_FAILURES_BEFORE_WAITING` and pinned by `policy_constants_match_the_apple_clients`) is what stops a captive portal — which reports a perfectly satisfied route while answering every request with a login page — from burning a whole backlog: after five consecutive transport verdicts the pass parks. **Apple counts per scope** (`consecutiveTransportFailures` is reset at each `drain(scope:)`) and resumes on a genuinely *new* satisfied path, tracked by a generation counter so a path landing between the decision to wait and the parking cannot be lost; **Linux counts process-wide** across its three workers (`Gates::note_verdict`) and parks them on `network_suspect`, a flag deliberately separate from GIO's `network_available` because GIO calls a captive portal reachable. Because nothing durable is written for a transport failure, parking costs the queue nothing — but a park with no way out would be worse than the bug, so Linux clears the flag on a route change, on a 60 s timer armed from `drain_completions`, and on every `schedule_background_pass`, which is what keeps Try Again from being a no-op. The re-queue trigger also differs: the Apple clients call `EnrichmentCoordinator.resume()` at the tail of `doReload()`, while Linux fires `enrichment::request_background_pass` on the scan-settled edge (both arms of `rescan()`'s consumer) because its scan thread commits tracks the reload has not read yet; and Linux derives job *activity* from requests in flight (`enrich_in_flight`) rather than from the due count, since a hundred albums a transport failure left pending are still due while nothing is being worked on.
- **The AI pass has three different ways to stop, and "Waiting for a connection" is only one of them.** Every failure of the AI proxy used to come back as `.transport`, so a spent daily allowance retried for 70 s per request, then after five in a row parked the job under "Waiting for a connection" while the Mac was online — and the park only lifted on a *network path change*, so nothing ever resumed it. The same misreport hid the day Groq withdrew its model. Now `GroqService` reads the proxy's answer through `FlaccyCore.AIProxyReply` (status + the `error` code in the body: `*_daily_limit_reached` is a spent allowance, any other 429 is upstream "busy" and keeps the 10/20/40 s backoff, everything else non-2xx is "unavailable") and an analysis returns an `AIAnalysis` (`music` + an `AIInterruption`), so what *was* identified is written even when the pass is cut off — the folder stays queued for the rest because the interrupted attempt records `.transport` (nothing durable) and resolves nothing. The decisions live in the pure `EnrichmentBreaker` (`observe` → `carryOn` / `waitForNetwork` / `needsEntitlement` / `pause`), unit-tested without a network: silence ×5 parks for the route, error answers ×5 pause the AI scope for `serviceRetryInterval` (15 min) as `Activity.serviceUnavailable`, and a spent allowance pauses it at the *first* sign as `Activity.dailyLimit` with `resumesAt`. The pause belongs to the AI scope only (`EnrichmentCoordinator.aiPause`): album and artist enrichment keep running underneath, a pass started meanwhile skips the AI scope without asking, a timer wakes it, and a pass that ends with AI still asleep re-publishes the pause as its last word so "why isn't it moving" never disappears with the quiet. The reset moment is the proxy's `Retry-After` (seconds to the next **UTC** midnight — the day the limiter counts — plus one second), not the local calendar: a device whose clock runs a minute fast would otherwise wake early, hit the limit again and sleep a whole extra day; `EnrichmentPolicy.nextQuotaReset` is only the fallback for a proxy that sends no header. Surfaces say it in their two slots through `EnrichmentJobCopy.pause(for:)` ("Daily AI limit reached" / "Resumes at 3:00 AM", "AI is unavailable right now"), `Activity.isPaused` keeps the ambient chrome for all three stops, the Debut summary no longer waits out its 90 s curtain once the allowance is spent, and the watch swaps its ring for `wifi.slash` / `hourglass` / `exclamationmark.triangle`. Linux never calls the proxy and never reports these, but `Activity::DailyLimit` / `ServiceUnavailable`, `resumes_at`, `next_quota_reset` and the copy are mirrored in `linux/shared/src/enrichment_job.rs` (clock shown as 24-hour local there, the one recorded divergence) and `EnrichmentFailure`/`Failure` deliberately gained no case on either side.
- **The Debut's second act must never be skipped, and the shared director is where that is enforced.** `LibraryDebutDirector.advance(…, jobHeardFrom:)` reads a drained queue as "the job is over" — but the job's snapshot starts life `.idle` with nothing remaining, which reads as drained, so an act evaluated before the coordinator has published would jump straight from the load bar to the summary card and the AI showcase (the one thing justifying the unlock) would never render. Both Apple clients pass `heardFromJob || elapsedInFinishing >= 2` (`LibraryViewModel.jobHasSpoken`, `ContentRouter.jobHasSpoken`), the coordinator publishes its true `remaining` *before* the expensive page read so a 3 000-album library reports in time, and Linux does the same job with `Stage::ready_to_advance`'s `job_primed`. The 90 s curtain remains the hard ceiling on every client: a job that never reports can delay the card, never hold it.
- **Two root-cause bugs this feature killed, so nobody reintroduces them.** `saveAlbumCoverArtIfMissing` had zero callers, so `albumInfo.coverArtData` was always NULL, the "this album already has a cover" skip never fired, and every album re-enriched on a 24 h TTL forever; `insertTracks` now routes every insert through `hoistingCoverArt`, which is also what feeds the mosaic and what migration v10 backfills. On Linux, `apply_album_enrichment` stamped `lastFetched` unconditionally, so a single offline launch poisoned every queued album for 30 days; scheduling now lives only in `enrichmentState`, `lastFetched` is never stamped, and `apply_album_enrichment_no_longer_stamps_last_fetched` guards it. **`linux/src/` is UNVERIFIED for this change** — the crate has not been compiled since it landed, because it cannot build on the Mac; run it on the arch box before it ships.
- **An album is grouped by its release credit, not by who performs each track, and that credit is usually derived rather than read.** Grouping on the per-track artist shatters every compilation, soundtrack and split record into one album per performer — a 31-track score by seven composers became seven albums of four. `ALBUMARTIST` exists to prevent that, but most rips in the wild do not carry it, so honouring the tag alone fixes nothing for the libraries that have the problem. `FlaccyCore/Sources/FlaccyCore/Library/AlbumCredit.swift` ⇄ `linux/shared/src/album_credit.rs` decide the credit from both: a tag wins outright wherever one exists (a half-tagged album is best served by what somebody actually wrote down), otherwise a performer holding a **strict majority** (`dominantShare`/`DOMINANT_SHARE` = 0.5, pinned in both languages) takes the release and anything less concentrated is the literal, untranslated string `Various Artists` — the same string taggers write, so a derived credit and a tagged one collide. A credit cannot be decided one file at a time, so the scan stores only the tag and a settle pass fills in the rest once every track is on the table: `Db::resolve_album_credits` ⇄ `DatabaseManager.resolveAlbumCredits()`, both clustering by normalized album title **within the containing folder** (`Album/CD1` and `Album/CD2` resolve apart then regroup under the one credit they agree on) and falling back to the performing artist at the library root, where two unrelated "Greatest Hits" must stay apart. Both run from the library-read path, so they are idempotent and self-healing. The watch scans its own files rather than reading the phone's database, so it re-derives with `LibraryScanner.resolvingCredits` before grouping.
- **Three things the credit change had to fix that are not obvious from it.** (1) **Covers are hoisted per track, long before anything knows the release is a compilation**, so they land under the performing artist while the album surface asks by credit — `ADOPT_COVERS_FOR_CREDITED_RELEASES_SQL` / `adoptCoversForCreditedReleasesSQL` gives the credited release its own `albumInfo` row seeded from a member's, and runs **unconditionally, not gated on whether a credit changed**, because enrichment may fetch the cover many reloads after the credits settled. (2) **That adopted row must not answer for year and genre.** Enrichment deliberately keeps asking Last.fm under the *performing* artist — "Various Artists" is a name no provider can answer — so the answers land on the members' rows, and taking the credited row whole handed the album a NULL year the moment it gained its cover. `album_meta_for` / `DatabaseManager.albumInfo(title:credit:tracks:rows:)` resolve **field by field** across the release's rows. The enrichment seeds and the `flaccy_norm` composite-key rules are untouched on purpose. (3) **Crediting a compilation to Various Artists erases its performers from the Artists tab** unless the index counts performances too: `build_artists` ⇄ `LibraryViewModel.artists` union credits and performances, keeping `appearance_count`/`appearanceCount` apart from `album_count`/`albumCount` so a performer is never sold as an author, and every "tracks by artist X" path (`Core::artist_tracks`, `ownedTracks()` on both Apple artist pages, the avatar/cover indexes, `goto_artist`'s known check) resolves performances as well. Each client's artist page gained an **Appears On** shelf below Albums, and both are dropped rather than shown empty.
- **Linux 1.9.0 now-playing row indicator matches iOS, and goes further.** iOS already draws three animated equalizer bars in place of the track number with an accent-tinted title (`flaccy/AlbumDetailViewController.swift` `AlbumTrackCell`/`NowPlayingBarsView`); Linux mirrors it exactly (`controls::track_index_cell` + `attach_now_playing_row`, Cairo-drawn bars — GTK only re-measures CSS-animated `min-height` sporadically, so the stylesheet version barely moved). Linux applies it in album detail, playlist detail, the songs table and the queue panel. The Mac's playlist detail now observes `trackDidChange` and repaints its title column like the songs table does, so playlist rows light up there too. iOS now lights up playlist detail too (`PlaylistTrackCell` carries the shared `NowPlayingBarsView`); its songs *collection* view is the last surface without it, and the grid/compact cells would need a different treatment than a leading bars slot.
- **Interface zoom is a desktop feature, persisted on both desktop clients.** Ctrl+= / Ctrl+- / Ctrl+0 on Linux and ⌘= / ⌘- / ⌘0 on the Mac zoom the whole window in 10 % steps between 75 % and 200 %, with a Preferences/Settings row mirroring the same value; lyrics keep their separate size on top of it. The mechanisms differ because the toolkits do: Linux (`linux/src/ui/ui_scale.rs`) sets `gtk-xft-dpi` for every point-sized run of text, rewrites the stylesheet's `font-size: <n>px` declarations by the same factor before reloading the provider, and bumps `-gtk-icon-size` for symbolic icons — pixel-sized artwork keeps its measure; the Mac (`flaccyMac/Design/MacInterfaceScale.swift`) scales the unit square of one `InterfaceZoomHostView` under the window's content view. **On AppKit, Auto Layout against a bounds-scaled view resolves at frame size and ignores the transform** — so every zoomed surface, including the Now Playing overlay, is constrained against the host's `content` child whose frame is set by hand to the scaled bounds each layout pass (`RootContainerViewController.overlayHost`); the toolbar is native chrome and stays at system size. iOS scales with Dynamic Type instead, so there is nothing to port.
- **Now Playing panel state persists on Linux and macOS** (`np_show_lyrics` / `np_show_queue` / `np_swap_sides` in `linux/src/config.rs`, `NowPlayingLayout` in `flaccyMac/UI/NowPlaying/`). iOS's player is a single column with no side panels, so there is nothing to remember. Deliberately *not* persisted anywhere: the queue contents and playback position — that is session restore, a separate feature, not view configuration.
- **The Linux client idles when nothing on screen moves, and Now Playing no longer costs a GPU.** A playing Now Playing page with lyrics and the queue open took 12–30 % of an RTX PRO 6000's SMs at 60 Hz (the owner's instance showed 43–54 % on a 120–165 Hz display) and starved itself down to 7–50 frames a second, because `.np-backdrop { filter: blur(64px) }` — which the stylesheet claimed was "static, so cheap" — is a GPU blur of a window-sized picture that GSK re-runs for **every frame the window repaints**, and a scrolling lyrics column repaints all of them. The blur is now baked once, off the main thread, into a 96 px texture (`ArtworkCache::request_backdrop`, `Look::Backdrop`, centre 80 % of the cover, Gaussian σ 3.2 texels), drawn as one plain textured rectangle; the key still starts `title|artist|` so `invalidate` drops it with the covers. The rules that came out of finding the rest, so nobody reintroduces them: **no CSS `filter`, no animated `transform` or blurred `text-shadow` on text** (scaling re-rasterises every glyph on each frame of the transition: dropping the current lyric line's `scale(1.04)` + glow cut a playing lyrics column's main-thread time by over a third), **no infinite CSS animation** (an animated node keeps the frame clock cycling at the display rate even when its widget is hidden behind another page — the mini player's `play-pulse` glow and CSS equalizer bars did exactly that, so a playing library never let the window rest; the pill no longer pulses, the mini bars are the same Cairo `build_equalizer_indicator` the track rows use, and only an instrumental ♪ that is the *current* lyric line still breathes), and **no permanent `add_tick_callback`** (even an empty one asks for a cycle every vertical blank for the widget's lifetime; a `GtkProgressBar` that has ever been `pulse()`d keeps one for good, hidden or not — the `Idle` scan-progress event used to pulse the header bar once every library load had finished, so from 2026-08-21 until the fix of 2026-10-17 a resting window logged 60 empty frame-clock cycles a second on every launch; `ScanProgress` now sets the fraction for any phase that is not active, and a resting library, Now Playing and Now Playing with lyrics all log 0 cycles again). Width-driven adaptation goes through `ui::resize::watch_width`, which listens to the frame clock's *layout* phase — it runs only when something asked for a layout, and GDK repeats it until it settles, so what a callback shows or hides lands in the same frame; slow animation goes on timers that know when the picture next changes: the shared 25 Hz `Metronome` behind every playing equalizer indicator (ends itself when none is on screen), the seek bar's `next_wakeup` (the sooner of the head moving half a device pixel and a label's whole second turning over, 8–250 ms), and the lyrics `Follower`, which sleeps until the next line is due (≤ 1 s) and runs a frame callback only while a scroll spring is moving. Timers also stand down while the compositor has the window suspended (`ui::screen::is_watched`, `AppEvent::WindowSuspended` → seek bar, lyrics, `resume_bars`): minimized, the process sits at ~1 % CPU and ~12 wakeups a second. **Measure with `FLACCY_FRAME_STATS=1`** (`linux/src/frame_stats.rs` logs, once a second, frame-clock cycles and the main-thread milliseconds spent in the update, layout and paint phases; a resting window logs zeros) plus a nested `kwin_wayland --virtual --socket <name>` and `nvidia-smi pmon` for the process's SM % on the real GPU — never Xvfb, which has none. Before → after on a 2152×1346 window at 60 Hz: library playing 6.5 → 0.0 % SM and 11.9 → 7.4 % of a core; Now Playing 5.8 → 0.0 % and 30 → 4 %; with lyrics and queue 17.9 → 1.6 % and 54 → 7.6 %. Visible differences, all deliberate: the current lyric line is bold and accent-coloured but neither scaled nor glowing, the play pill no longer pulses, the seek head repaints at half a device pixel instead of a quarter (a four-minute track on a 2000 px bar: ~16 repaints a second, not ~33), and equalizer bars redraw at 25 Hz. **Apple clients are not affected** (Core Animation composites on its own; none of this is portable), and the Linux-only `FrameDriver`s that remain (`slider` emphasis, `Pinner`, the debut) run for a bounded time. **Trap for whoever measures next:** `pkill -f` / `pgrep -f` with a pattern that also appears in the Bash tool's own command line kills the tool's shell; keep stop commands in a script file. And `/tmp` here is an 8 GB tmpfs other sessions fill — build and bench into `~/.cache`, not the scratchpad.
- **Lyrics resolution is the same on all three clients** (`linux/src/lyrics.rs`, `flaccy/LyricsService.swift` — the latter compiles into both Apple targets): cache → the user's own `.lrc`/`.elrc` sidecar or an embedded lyrics tag (enhanced word tags kept, see the next entry) → lrclib, and on a 404 retry without the album name, then with the title's edition decoration and featuring credits removed (`clean_title`/`lead_artist`), before ranking `/api/search` results locally with the same weights (title .35 / artist .30 / duration .25 / has-synced .06 / album .04, hard-rejecting >15 s duration drift, accepting at 0.80). Misses cache for 30 days and are distinguished from network failures, which offer Retry instead of a permanent blank. Two deliberate differences: Linux reads tags with lofty while the Apple side asks AVFoundation, which surfaces fewer Vorbis-comment keys — the sidecar path is the reliable one there; and lyrics text size is user-configurable on Linux only (`lyrics_font_size`), because the Apple clients scale with Dynamic Type instead.
- **Lyrics are one shared document, remastered in 2026-10 — the model, the clock and the Lyricsfile reader are mirrored line for line.** `FlaccyCore/Sources/FlaccyCore/Lyrics/` ⇄ `linux/shared/src/lyrics/` (`bash scripts/test-shared.sh` proves both: 50 Rust and 58 Swift lyric tests, the Swift side carrying a few extra edge cases) turn an LRC, an enhanced LRC (`<mm:ss.xx>` word tags, a trailing tag closing the last word, text before the first tag riding the line start, angle brackets that are not timestamps kept as text) or a **Lyricsfile 1.0** (the open CC0 YAML lrclib now ships on every record as `lyricsfile`, with a `hasWordSync` flag, read by a deliberately restricted YAML subset reader that refuses a duplicate key, tag, alias, tab, unknown version or unterminated quote by returning nil so the caller falls back to the LRC text) into `Document { lines, plain, instrumental }`. Every line always knows where it ends: a stated `end_ms` wins, then the end of its last timed word, then the first blank-stamp break after it, then the next line, never past `MAX_INFERRED_HOLD` (10 s). Lines stamped together share an end; overlapping lines are allowed and `highlighted(t)` lights them together (`OVERLAP_LOOKBACK` 8). A gap of at least `MIN_INTERLUDE` (4 s), the intro included, becomes an `Interlude` line of its own — which is why a list of rows still maps one to one onto `lines` — and a line of only music notes (lrclib writes `♪`) is a break, not a lyric. A line wrapped entirely in one pair of parentheses is backing vocals. `primary_index(t)` (the last line started) is where scroll and emphasis live; `text_at(t)` goes blank after a line ends (the seek-bar hover bubble); `next_boundary(t)` is the next instant anything on screen can change (Linux sleeps until then); `Line::progress(t)` is `NotStarted | Singing{word, fraction} | Done`, and a lit interlude shows `INTERLUDE_BEATS` (3) beats that light across its length. The listener's timing correction (`offsetMs`, ±10 s in 100 ms steps, **positive = lines come later**, applied as `position − offset` to the clock, never to the lines, remembered per track in the lyrics row and never overwritten by a refetch) lives on `Lyrics`, with Earlier/Later/Reset behind a clock button on every client — a popover on Linux, a menu on the Mac, a menu that stays open between presses on iPhone. The LRC `[offset:]` tag is deliberately ignored because players disagree about its sign. **Cache rows carry `lyricsfile`, `offsetMs` and `revision`** (Apple migration v14, `ALTER TABLE` in `Db::migrate`): content stored before revision 2 is asked for again once and kept if the server cannot improve on it or cannot be reached, a miss stands 30 days, and lrclib's 429/5xx are retried once after `Retry-After` clamped to 0.3–3 s (it answered 503 to a burst of searches while this was built). - **A flood of flushing seeks wedges PulseAudio for good, so the Linux player serializes them (1.16.0).** The old seek bar called `seek_simple` on every motion event — every ~6 ms on a 165 Hz display — and pulsesink (PipeWire's pulse server included) then sat in PLAYING with a frozen position that neither pause/play nor another seek revives; only reopening the stream does (reproduced with a bare playbin3, never with fakesink). `linux/src/player.rs` now keeps one seek settling at a time, ≥70 ms apart, newest target wins, with `position()` reporting the target meanwhile; a drag chases with keyframe seeks and the release lands one exact seek — the coalescing the Apple clients' `chaseSeek` already does — and targets stop 0.25 s short of the end like `clampedSeekTarget`. Two playbin3 traps sit next to it: `about-to-finish` fires once per item and never again after a seek, and a seek issued once the next track is queued can jump straight into it, so an item that has drained is *reopened* at the target (paused, seeked, resumed) rather than seeked, which also keeps the hand-off gapless; and a stall watchdog on the playback tick reopens a pipeline that claims to play but has not moved for 2.5 s, standing down after two tries so slow storage never loops. `FLACCY_DEMO_SCRUB_DRILL=1` replays display-rate drags, a drag held past the end, a held skip key and a seek after the next track was queued against the real sink, logging PASS/FAIL. - **Music video mode is Linux-only, for the same reason Downloads is** (`linux/src/musicvideo/`, `linux/src/ui/video_view.rs`). The Now Playing lens swaps the hero artwork for the song's music video: a second `playbin3` decodes picture only into a `gtk4paintablesink` paintable while the lossless file on disk stays the clock. Four pieces worth knowing before touching it. (1) **The pipeline flag `video+download` is load-bearing** — streamed straight from HTTP, playbin refuses every seek, and seeking is how the picture is held to the audio; with download buffering the measured drift goes from a permanent five seconds to ≤60 ms. (2) **Format selection must demand `protocol^=http`** — YouTube also offers the same video as HLS, whose segments need a transport-stream demuxer many installs lack; a decoder failure retries once in H.264 (`stream::format_selector`). (3) **The video is not the album master** — runtime is bounded by *ratio* (0.5–1.9×), never by seconds, because official videos are routinely a minute shorter than the album cut; the offset between the two timelines is measured by cross-correlating spectral-flux onset envelopes of both recordings (`musicvideo::align`, pure Rust FFT, no new system dep) and cached forever. (4) **Picking the right result is scored, not guessed** — uploader identity and view count carry it, because every re-upload copies the title; a local Ollama model only breaks ties the scorer calls close, and its verdict is blended rather than obeyed (`score.rs`, `llm.rs`). Not portable to the Apple clients: it shells out to `yt-dlp`, and App Review Guideline 5.2.3 rules out an App Store build that streams YouTube. If it ever comes to the Mac outside the App Store, `FlaccyCore` should get the scorer and the aligner; the pipeline would be `AVPlayer` with the same governor.

- **Sleep-at-end-of-track stops on the boundary on all three clients, and the resume differs on purpose.** Both players used to pause *after* the next track had already started — `completeAutoAdvance` on Apple, `AppEvent::TrackChanged` on Linux — so the listener heard the opening of the next song and woke to a queue one track along. iOS/macOS set `actionAtItemEnd = .pause` while the request stands and complete the stop from `AVPlayerItemDidPlayToEndTime`; Linux withholds the next URI from playbin's `about-to-finish` and consumes the flag in `on_eos`. - **Downloads (paste a YouTube/etc. link → best audio → library) is Linux-only** (`linux/src/downloads.rs`, `linux/src/ui/downloads.rs`, shipped 1.6.0). Deliberate: it shells out to `yt-dlp`/`ffmpeg`, which iOS/watchOS cannot run, and an App Store build that rips YouTube audio would violate App Review Guideline 5.2.3 regardless of implementation. If this ever comes to the Apple side, it needs a different design (e.g. user-provided files via the existing document-picker import, or a Mac-only build outside the App Store) — do not port the yt-dlp approach. **A download is not finished until this machine can decode it.** YouTube serves plenty of tracks as AAC only, and AAC needs `gst-libav`, which the base runtime deps don't pull in — the download succeeded, the library indexed it, and the failure surfaced as a missing-codec toast the first time the user pressed play. So the pipeline now prefers Opus (`-S acodec:opus`, which is also the better-sounding stream and is decoded by `gst-plugins-base`) and then *proves* the result: `is_decodable` prerolls the file through `uridecodebin` to PAUSED and requires a linked audio pad, and anything that fails is re-encoded to FLAC by ffmpeg (`transcode_to_flac`) — lossless from an already-lossy source, so no second generation loss, with cover art carried across by hand because ffmpeg will not turn an MP4 cover atom into a Vorbis picture block. A launch also sweeps the downloads a pre-conversion Flaccy left behind (`repair_unplayable`), which is why `downloads.codecChecked` exists: without it the sweep would re-preroll the entire download history on every launch, and every `set_download_file` caller has already been through `ensure_playable`, so storing the path is what marks the row.

- **Equalizer audio-path rules that an independent review had to teach us.** (1) A kernel born with the beginning of a song starts *engaged* (`startsEngaged`, set by the engine for any item under 0.25 s in); one that appears under a song already playing fades in over 1 024 frames so enabling mid-song does not click. Fading in every new tap, as first written, glided each track's opening in from 0 dB over 23 ms. (2) The peak guard's ceiling is **full scale (1.0), not −1 dBFS**: at −1 dBFS it limited every hot master the moment the equalizer was switched on, with 4 % distortion on bass, and made Compare an unfair A/B. The guard keeps the stage out of bypass until it has released, so there is no gain step on hand-over. (3) Filter state and coefficients are double precision; float32 left −71 dBFS of arithmetic noise at 96 kHz and −64 at 192 kHz on a 28 Hz high-pass. (4) `Double("nan")` parses: every number read from profile text goes through `finiteNumber`, `EqualizerBand.clamped()` turns NaN into a usable band, and the kernel skips a band whose coefficients are not finite, because one NaN in the delay line silences the rest of the track. (5) The tap's kernel reference sits behind a lock (render threads only `withLockIfAvailable`), and spectrum demand is counted per screen (`beginAnalysis(for:)`), because a cancelled interactive dismissal calls `viewWillAppear` again without a `viewDidDisappear` and used to leave a tap attached forever. (6) Linux dithers 16-bit output, and only samples the stage changed, so a sample already on a step stays bit-exact. **Known gap:** `Headroom` and the graphic solver are computed at the 48 kHz reference rate while the kernel builds each biquad at the stream's real rate, so at 96 kHz a high band can land up to ~0.8 dB from the drawn curve and a +12 dB shelf at 16 kHz is attenuated ~2.5 dB too much (at 44.1 kHz the auto preamp is ~0.5 dB short and the guard catches it); fixing it means publishing per-rate variants of the resolved bands and preamp.

On the Mac that lives in `flaccyMac/UI/Detail/` — `TrackPageFrameView` (modes, rail, clamp), `TrackPageSongs` (control strip: filter, show-the-playing-song, List / Table / Columns, remembered in `flaccy.mac.detailLayout` and shared by both pages), `TrackBlocksSurface` (List and Columns, disc headers from `TrackOrdering.sections` ⇄ Rust `disc_sections`), `TrackTableSurface` (sortable table, as tall as its rows inside a scroll view that hands the wheel to the page, columns dropping out by width, equalizer bars and accent text on the playing row) and `PlaylistListSurface`. **Mac playlists reorder in List through a real `NSTableView`** (native multi-row drag, delete key) rather than a stack of rows, so List and Table are two table views over one model; reorder stays List-only and the Table's hint line says so. Two AppKit traps found here: macOS 27 throws `NSInternalInconsistencyException` from `NSStackView.removeArrangedSubview` for a view that is not arranged (guard with `arrangedSubviews.contains`), and a constraint-laid-out view's `setFrameSize` is **not** reliably called on live resize, so width-driven modes are evaluated in `layout()`. Recorded gaps: the Mac playlist page still has no ambient backdrop (Linux has one), disc labels (`Disc 1`, `Side A`) are English on every client, and a 1000-song album builds its List rows eagerly (about a second; the Table takes half that).
- **Watch sync is a ledger, a transcoder and a heartbeat, on iPhone and watchOS only (macOS has no WatchConnectivity and Linux has no watch: a recorded gap, not an oversight).** A track's identity across the two devices is its **stem** (`SyncStem.of`: canonical relative path minus an audio extension), because the phone sends an AAC re-encode of a FLAC; the watch holds at most one file per stem and a delivery deletes its same-stem siblings. Everything the phone knows lives in one pure state machine, `FlaccyCore.WatchSyncLedger` (queued, preparing, sending, awaitingAck, onWatch, waiting with backoff, diskFull, stuck), and **the watch's heartbeat is the only authority**: `ingest` turns every confirmed stem into `onWatch` and drops all transitional state for it, which fixed the old wedge where a transfer that finished while nobody watched (iOS 17.5+ often never calls `didFinish`; `observe` is attached with `.initial` for that reason) stayed "in flight" forever and blocked reconcile. The pipeline hands WatchConnectivity at most 4 tracks / 150 MB at a time, backs off 20 s ×3 up to 15 min, gives up after 8 attempts (`retryStuck` is the user's button), and `WatchSyncService` (iOS) only feeds the ledger events: it will not pump until the first heartbeat arrives (or `receivedApplicationContext` is empty on a fresh install) and it withdraws a requested track missing from the library only once the library is non-empty, because an empty library at launch means "not loaded yet". **Bytes are the product:** `WatchAudioProfile` is Original or AAC-LC 256 (default, `high`) / 192 / 128 kbps, the watch plays over Bluetooth which is lossy anyway, and `WatchTranscoder` encodes at a constant bit rate (variable undershoots the target by 40-75% on quiet material, so `estimatedBytes` would lie), never re-encodes a lossy source, never produces a file bigger than its source (passthrough at or below 1.15× the target rate, and a post-encode fallback), embeds a 400 px cover and the tags, and is gapless (AVAssetWriter writes priming 2112 and `iTunSMPB`); a quality change affects only music sent from then on. `bash scripts/watch-transcode-harness/run.sh` proves it (443 checks, real FLACs found on the Mac are used in place and never copied). Phone to watch also carries `SyncBatch` ("Receiving 3 of 12") next to the enrichment job in the ONE application context (it replaces the previous one wholesale, so it always carries both). Watch to phone carries `removed` (a deletion on the wrist, so it is not re-sent) and `plays` (`WatchPlayLog` persists them and hands them to `transferUserInfo` in batches of 50; `WatchPlayLedger` dedupes by id on the phone; `WatchPlayIngestor` bumps the play count, writes the scrobble row and flushes Last.fm; the qualifying rule is `meetsScrobbleCriteria`'s). A long sync survives the app being backgrounded through a `BGContinuedProcessingTask` on iOS 26+ (one task per run, identifier `<bundle>.watchsync.<uuid>` registered at submit time because a wildcard handler is blocked, both the exact and wildcard names in `BGTaskSchedulerPermittedIdentifiers`, `.fail` strategy, progress reported per song; verified on the iPhone Air: submitted and the handler ran) with `beginBackgroundTask` as the fallback, and the watch handles `WKWatchConnectivityRefreshBackgroundTask` in `WatchBackgroundTasks`. **Verifying it:** the simulator pair accepts `transferFile` but never delivers the file, and a stale queue from earlier runs stalls delivery for minutes, so run `--exercise-watch-sync --seed-screenshots` on the phone of a FRESH pair (it asks the watch to materialise each handed-off file through a simulator-only `debugDeliver` command and logs PASS/FAIL for delivery, smaller bytes, idle, re-request sends nothing, removal, original quality) and `--exercise-receive` on the watch (receiver logic with synthesized files: replace by stem, wrong size refused, `../` refused, remove by stem); `--exercise-watch-bgtask` runs the background task alone on a device. **Not yet seen:** a real file delivery to a real watch (the Series 6 was unreachable and had no watch app installed). **Packaging traps this work found:** the watch target had never shipped its `Localizable.xcstrings` or `PrivacyInfo.xcprivacy` (its Resources phase held only the asset catalog), so the wrist was English-only and carried no privacy manifest: `project.yml` compiles the whole watch folder, which carries both, and `python3 scripts/check-strings.py --watch build/dd-watch-main` checks the watch catalog; a new iOS-only file in `flaccy/` must be added to the `flaccyMac` target's `excludes` in `project.yml` or the Mac build compiles it.

## Midgar platform (MidgarKit 4.3.1)
- **Build**: Swift 6 language mode with strict concurrency, approachable concurrency and MainActor default isolation on every Apple target, warnings as errors in Release. FlaccyCore is Swift 6 too and nonisolated. Types that work off the main thread are `nonisolated`; a closure that Apple calls on its own queue (a Combine operator on a notification, `MPRemoteCommand`, `MPMediaItemArtwork`) must not inherit MainActor, or Swift 6 traps at runtime: use a `nonisolated` function, `@Sendable`, or `onMainActorSync`.
- **Identity and portal**: `FlaccyMidgar` (iOS and Mac) builds the Midgar ID (`MidgarIdentity`, keychain groups `$(AppIdentifierPrefix)$(PRODUCT_BUNDLE_IDENTIFIER)` then `$(AppIdentifierPrefix)cc.midgarcorp.shared`, no App Attest entitlement), the portal configuration with the authorized client for Settings, and MidgarSignals. It runs from the app delegates before anything else. The watch app uses none of it.
- **Gateway**: `FlaccyAPIClient` is the only code that talks to flaccy-api, at `https://api.midgarcorp.cc/v1/flaccy/...` with `X-App-ID: flaccy` (AI metadata proxy, Last.fm signing, the sample album). The AI route reads the proxy's string `error` codes from the raw reply, which `MidgarHTTPClient` does not keep for a 429, so that one call uses a plain `URLSession`.
- **Reviews**: `ReviewPrompt` reports each completed song to `MidgarReviewPolicy`; `LegacyReviewState` carries the old ask dates over once.
- **Secrets**: `LastFMService.configure(apiKey:)` copies the Last.fm key from `Secrets` at launch, because `Secrets` is main-actor isolated and the gitignored file cannot be changed for the build.
- **Purchases are unchanged**: RevenueCat still sells Pro, `engine = "rc-full"` in the registry.

## Key Technical Details
- **Database**: GRDB (SQLite) for library persistence, metadata, scrobble queue
- **AI**: Claude Haiku 5.5 via the flaccy-api proxy Worker (guitaripod/flaccy-api, flaccy-api.midgarcorp.cc, secret `ANTHROPIC_API_KEY`) for music identification and metadata cleanup — no API key in the app. The shipped clients still speak the OpenAI chat-completions shape and still name `GroqService` and a llama model they never read; the Worker alone translates to the Messages API and picks the model, so a model swap needs no app release. Deliberately not routed through mako: it meters per-user credits behind a tenant and wallet, while Flaccy's AI is bundled with the entitlement and keyed only by anonymous device and IP quotas in the Worker. A request that fails on our side (upstream 429/5xx, which includes a missing or revoked key) is **refunded** against those quotas (`RateLimiter.refund`): before that, the day Groq withdrew its model every failed call still counted, and the Mac's whole 150-request device allowance was gone by noon, locking AI out until 00:00 UTC. Caps are `DEVICE_DAILY_LIMIT`/`IP_DAILY_LIMIT`/`GLOBAL_DAILY_LIMIT` in `flaccy-api/wrangler.jsonc` (600/1000/5000 since 2026-10-12, sized for Haiku 5.5; the global cap is the spend ceiling); one request is one album's batch. Deploy the Worker with `npx wrangler@4.149.0 deploy` — the version pinned in the repo fails against Cloudflare's current API.
- **Scrobbling**: Last.fm API with ASWebAuthenticationSession OAuth. **The Last.fm shared secret lives only in the flaccy-api Worker** (`LASTFM_SECRET`, set with `wrangler secret put`): every signed call (`auth.getToken`, `auth.getSession`, `track.scrobble`, `track.updateNowPlaying`, `track.love`, `track.unlove`) asks `POST /v1/lastfm/sign` for its `api_sig` with the same `X-Device-ID` the AI route uses (`LastFMService.requestSignature`, `linux/src/lastfm.rs`), and read-only methods stay unsigned. Signing counts against the same per-device/IP/global quotas as AI. Session keys stay on device. Neither client holds the secret, so an old `Secrets.swift` still carrying `lastFMApiSecret` is harmless and should be trimmed.
- **Audio**: AVQueuePlayer for gapless FLAC playback
- **UI Pattern**: Fully programmatic UIKit (no storyboards/XIBs)
- **Architecture**: MVVM pattern throughout
- **Target**: iOS 18, iPhone only
- **Scene Management**: Root view controller set programmatically in `SceneDelegate.scene(_:willConnectTo:options:)`

## Development Patterns
- Follow the existing programmatic UI approach - no Interface Builder
- Use UIStackView's heavily to simplify the layout code. UIStackView's are very configurable and performant.
- Always use the latest UIKit APIs like diffable datasource
- Use MVVM architecture for all screens
- UIKit only - No SwiftUI
- Keep view controllers focused - delegate business logic to view models. Use latest UIKit API like diffable datasource etc.
- Prefer Protocol-Oriented-Programming over Object-Oriented-Programming
- **Logging**: Use `MidgarLog` (MidgarCore) for all logging - never use `print()` statements. `FlaccyLogging.configure()` names the file `Library/Logs/flaccy.log` at launch on iOS, Mac and watchOS, and the categories (auth, connectivity, content, database, performance, playback, purchases, sync, watch, plus MidgarLog's own ui and general) are `MidgarLog.Category` constants in FlaccyCore. A warning is `MidgarLog.notice`.
- **Code Style**: Never use comments or MARK statements - code should be self-documenting through clear naming and structure
