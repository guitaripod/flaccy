# CLAUDE.md

## Cross-client parity (read first)

**Flaccy is the product, not any single app.** It ships as four clients — iOS (`App/`, `Features/`), macOS (`Platforms/mac/`), watchOS (`Platforms/watch/`), and Linux (`linux/`, Rust + GTK) — and they must be **as great and in-sync as possible**. A feature, fix, or behavior that lands on one client is incomplete until it lands on the others (or the gap is deliberately recorded).

- **When you change behavior on one client, port it to all the others in the same unit of work.** If a client genuinely can't get it (platform limitation) or you can't verify it (e.g. no Xcode on this Linux box), say so explicitly and leave a tracked note — never silently ship a one-client fix.
- **Share logic, don't fork it.** The three Apple clients share `FlaccyCore` (pure Swift/Foundation where possible) — put cross-client logic there and route every call site through it instead of copy-pasting sorts/parsers. The Linux client is a separate Rust codebase, so it mirrors the same behavior in Rust; keep the two implementations semantically identical and cover both with tests.
- **Linux points to the Apple apps; the Apple apps do not point back (by design, 2026-11-13).** Flaccy for Linux is free and is the funnel into the paid Apple apps: the Flaccy Server Connected page carries a note and a Get Flaccy for iPhone and Mac button, and About → Details links the same App Store page (`linux/src/apple_apps.rs`, one constant: give it the App Store campaign `pt`/`ct` parameters once the provider token is known). Never a popup, banner or nag on Linux.
- **Parity applies to behavior AND experience.** Ordering, grouping, metadata handling, naming, empty states, and the overall feel should match across clients, adapted to each platform's idioms (UIKit / AppKit / SwiftUI / GTK) — not reinvented.
- Pure shared logic (e.g. `FlaccyCore` ordering/parsing) can be compiled and unit-tested standalone on this Linux box via swiftly even when the full app can't build here — use that to verify cross-client logic before claiming it works.

- **Search finds across the whole library from Home on Linux and in the Search tab on iPhone; the Mac's search box still does nothing on Home (2026-11-20).** One rule decides a match on every client (`LibrarySearch` in FlaccyCore, `linux/shared/src/library_search.rs`, the same vectors on both sides): case and accents are folded, punctuation is read both as a word break and as nothing ("acdc", "ac dc" and "AC/DC" meet, "dont" finds "Don't"), the query is cut into words and every word must be somewhere in the row in any order and any field ("beatles abbey" finds Abbey Road), and a name of nothing but symbols ("÷") is matched as written. Every filter box uses it: the library lists, playlist pages and Add Songs on iPhone and iPad, the Mac's Songs, Albums, Artists and Playlists, and every Linux page. `rank` orders results (the name is the query, begins with it, every word begins a word, every word is in it, only the other fields answer), judging the name by the words the artist or album did not already answer, so "metallica one" leads with Metallica's One; songs past a title that begins with the query are one group. Linux shows a results page (`linux/src/search.rs`, `ui/search.rs`: Artists, Albums, Songs, Playlists, best first, then most played, then by name; "Show All N" opens that kind's page under the same search; Enter opens the first result) whenever a query is typed over Home, Stats, Wantlist, Downloads or Guide, pops a pushed page back to it, and gives the page back when the box is cleared or the sidebar is used. The iPhone Search tab orders by the same rank and keeps the person's sort order between equal answers, where Linux uses plays. The Mac has no results page: its search box filters Songs, Albums, Artists and Playlists and is ignored on Home. `FLACCY_DEMO_SEARCH=<query>` (with `FLACCY_DEMO_SEARCH_ENTER=1`) types into the Linux box for a screenshot.
- **Music plays again after another app took the sound, on iPhone and iPad only (2026-11-20).** Flaccy used to resume only when iOS said to (`.shouldResume`: a call, Siri, an alarm, an app that deactivates with `notifyOthersOnDeactivation`). Most apps never hand back: a video in a feed, a game or a voice message just stops and the system tells nobody, so the music stayed paused. Settings › Playback › After Another App Plays now chooses `FlaccyCore.InterruptionResume`: `whenQuiet` (the default, "Resume"), `whenHandedBack` ("Calls and Siri Only", the old behavior) or `never` ("Stay Paused"). For `whenQuiet`, `InterruptionResumeWatcher` samples `AVAudioSession.isOtherAudioPlaying` once a second under a background task and `InterruptionQuietWatch` decides: behind another app it plays again only after that app **was heard and then stayed quiet for two samples**, because `isOtherAudioPlaying` is false the whole time for an app that took the session to record (measured), and taking the session back would cut a recording short; with Flaccy on screen quiet alone is enough. Measured on the iPhone XS (iOS 18.7) and the iPad Pro (iPadOS 27) with a second app that plays a tone and stops without deactivating: resumed 2 s after the tone stopped; **the background task lasts 26 s on both**, after which the app is suspended and nothing can be heard, so a longer interruption resumes on the return to Flaccy (within 1 s); coming back also delivers the system's late "ended" with `shouldResume` false, which is why that case keeps waiting instead of clearing the flag. Any press of play or pause, a sleep timer or a lost route ends the wait (`userPausedPlayback` and `isPlaying` clear `wasPlayingBeforeInterruption`). `activateAudioSession()` now reports a refusal, so a call in progress leaves the wait running instead of flipping the UI to playing. Not built: mixing with other apps (`.mixWithOthers`), which would keep the music going under everything but costs the lock screen and Control Center player, since a mixable session cannot be the Now Playing app. Not verified: Siri and a phone call under `whenQuiet` (neither can be driven from the Mac). `--exercise-interruption` proves each path; a locked device never puts an app on screen, so the return path needs an awake one, and the interrupting test app must use the scene lifecycle or iPadOS 27 will not launch it. **Recorded gap:** the Mac and Linux mix every app's sound and have no interruptions; the watch keeps the system's hand-back only (`WatchAudioPlayer.handleInterruption`) and has no setting.
- **Linux Albums shows an album whole under the Offline chip (2026-11-20).** iPhone and the Mac narrow an album to the songs that play offline (and to a source chip's songs); Linux keeps any album with one such song and shows all of it (`filters::albums_allowed`), and has no source chip on Albums. - **The job's circuit breaker and its re-queue trigger differ by platform on purpose, and both are load-bearing.** `EnrichmentPolicy.transportFailuresBeforeWaiting` (5, mirrored as `job::TRANSPORT_FAILURES_BEFORE_WAITING` and pinned by `policy_constants_match_the_apple_clients`) is what stops a captive portal — which reports a perfectly satisfied route while answering every request with a login page — from burning a whole backlog: after five consecutive transport verdicts the pass parks. **Apple counts per scope** (`consecutiveTransportFailures` is reset at each `drain(scope:)`) and resumes on a genuinely *new* satisfied path, tracked by a generation counter so a path landing between the decision to wait and the parking cannot be lost; **Linux counts process-wide** across its three workers (`Gates::note_verdict`) and parks them on `network_suspect`, a flag deliberately separate from GIO's `network_available` because GIO calls a captive portal reachable. Because nothing durable is written for a transport failure, parking costs the queue nothing — but a park with no way out would be worse than the bug, so Linux clears the flag on a route change, on a 60 s timer armed from `drain_completions`, and on every `schedule_background_pass`, which is what keeps Try Again from being a no-op. The re-queue trigger also differs: the Apple clients call `EnrichmentCoordinator.resume()` at the tail of `doReload()`, while Linux fires `enrichment::request_background_pass` on the scan-settled edge (both arms of `rescan()`'s consumer) because its scan thread commits tracks the reload has not read yet; and Linux derives job *activity* from requests in flight (`enrich_in_flight`) rather than from the due count, since a hundred albums a transport failure left pending are still due while nothing is being worked on.
- **The AI pass has three different ways to stop, and "Waiting for a connection" is only one of them.** Every failure of the AI proxy used to come back as `.transport`, so a spent daily allowance retried for 70 s per request, then after five in a row parked the job under "Waiting for a connection" while the Mac was online — and the park only lifted on a *network path change*, so nothing ever resumed it. The same misreport hid the day Groq withdrew its model. Now `GroqService` reads the proxy's answer through `FlaccyCore.AIProxyReply` (status + the `error` code in the body: `*_daily_limit_reached` is a spent allowance, any other 429 is upstream "busy" and keeps the 10/20/40 s backoff, everything else non-2xx is "unavailable") and an analysis returns an `AIAnalysis` (`music` + an `AIInterruption`), so what *was* identified is written even when the pass is cut off — the folder stays queued for the rest because the interrupted attempt records `.transport` (nothing durable) and resolves nothing. The decisions live in the pure `EnrichmentBreaker` (`observe` → `carryOn` / `waitForNetwork` / `needsEntitlement` / `pause`), unit-tested without a network: silence ×5 parks for the route, error answers ×5 pause the AI scope for `serviceRetryInterval` (15 min) as `Activity.serviceUnavailable`, and a spent allowance pauses it at the *first* sign as `Activity.dailyLimit` with `resumesAt`. The pause belongs to the AI scope only (`EnrichmentCoordinator.aiPause`): album and artist enrichment keep running underneath, a pass started meanwhile skips the AI scope without asking, a timer wakes it, and a pass that ends with AI still asleep re-publishes the pause as its last word so "why isn't it moving" never disappears with the quiet. The reset moment is the proxy's `Retry-After` (seconds to the next **UTC** midnight — the day the limiter counts — plus one second), not the local calendar: a device whose clock runs a minute fast would otherwise wake early, hit the limit again and sleep a whole extra day; `EnrichmentPolicy.nextQuotaReset` is only the fallback for a proxy that sends no header. Surfaces say it in their two slots through `EnrichmentJobCopy.pause(for:)` ("Daily AI limit reached" / "Resumes at 3:00 AM", "AI is unavailable right now"), `Activity.isPaused` keeps the ambient chrome for all three stops, the Debut summary no longer waits out its 90 s curtain once the allowance is spent, and the watch swaps its ring for `wifi.slash` / `hourglass` / `exclamationmark.triangle`. Linux never calls the proxy and never reports these, but `Activity::DailyLimit` / `ServiceUnavailable`, `resumes_at`, `next_quota_reset` and the copy are mirrored in `linux/shared/src/enrichment_job.rs` (clock shown as 24-hour local there, the one recorded divergence) and `EnrichmentFailure`/`Failure` deliberately gained no case on either side.
- **A folder that is already tagged is never sent to the AI (2026-11-20), on iPhone, iPad and Mac.** Every imported song starts `aiAnalyzed = 0`, so every folder used to cost a model call whether its tags were perfect or absent: a library tagged with care spent days of allowance to have the model rewrite titles, credits and track numbers that were already right. `AIIdentificationTask` now reads the folder's tags before anything else (`AudioMetadataReader`, no artwork, stopping at the first file that falls short) and asks `FlaccyCore.TagCompleteness`: when every file has a title, an artist, an album and a track number of its own, the folder's `aiBatch` record is settled as identified and nothing is sent. The songs keep `aiAnalyzed = 0`, because that flag is also the count of songs the AI cleaned up (the Debut card, Settings) and these were not. A ripper's placeholders (`Unknown Artist`, `Unknown Album`, `Track 03`) are not tags, a file without a track number is not complete (the album would list out of order), one incomplete file sends the whole folder so the model sees its context, and a file that cannot be read counts as untagged. - **An album is grouped by its release credit, not by who performs each track, and that credit is usually derived rather than read.** Grouping on the per-track artist shatters every compilation, soundtrack and split record into one album per performer — a 31-track score by seven composers became seven albums of four. `ALBUMARTIST` exists to prevent that, but most rips in the wild do not carry it, so honouring the tag alone fixes nothing for the libraries that have the problem. `Core/FlaccyCore/Sources/FlaccyCore/Library/AlbumCredit.swift` ⇄ `linux/shared/src/album_credit.rs` decide the credit from both: a tag wins outright wherever one exists (a half-tagged album is best served by what somebody actually wrote down), otherwise a performer holding a **strict majority** (`dominantShare`/`DOMINANT_SHARE` = 0.5, pinned in both languages) takes the release and anything less concentrated is the literal, untranslated string `Various Artists` — the same string taggers write, so a derived credit and a tagged one collide. - **Lyrics and music videos are prepared ahead of time on Linux (2026-11-01); the Apple clients have a lyrics-only lane of their own (2026-11-03, next entry), no video.** `linux/shared/src/precache.rs` is the pure planner (tested): `chance_of_play` from queue distance, album in progress and the listener's 30-day and total plays; `wanted_videos` gives the next 3 queue entries a video *file*, the next 10 and the rest of the playing album a *match + alignment*, and habit (≥ 0.25 chance, capped at 200) a file; `lyrics_order` ranks the queue, habit and new arrivals (the whole library when `lyrics_whole_library` is on, which it is by default since 2026-11-03: see the next entry); `make_room` evicts the lowest chance-per-byte file only when the newcomer is 1.5× likelier, never a pinned one or one made or played in the last 24 h; `effective_budget` keeps 5 GB or 5 % of the disk free; `retry_delay_seconds` backs off by `Failure` kind with 30 % jitter. `src/precache/` is the coordinator (`mod.rs`: events → 1.5 s settle → a plan for each lane, gated by `blocker`: offline or a metered connection), the lyrics lane (`lyrics_lane.rs`, one song at a time through `lyrics::fetch_shared`) and `governor.rs`: **one `LRCLIB` gate shared by the lyrics panel and the lane** (450 ms between requests, a 429 starts a cooldown for the *full* `Retry-After` plus up to 30 %, and a request that would fall inside it is not sent), a `YOUTUBE` gate (6 s plus jitter between the lane's yt-dlp runs) and a `Breaker` (a refusal rests the lane at once, a hiccup needs three). A file is only used by the ceiling it was fetched under, so changing Quality refills. **Not built: pinning ("Keep offline") has its column and eviction rule but no UI; the first 10 MiB chunk is fetched before the budget check; the lane does not yield to a video playing in the foreground.** Verification: unit tests with a stub HTTP server (resume, ignored ranges, truncated bodies, 403/429/5xx, no room, floor, restart reconcile, eviction), `FLACCY_REAL_VIDEO=<id> cargo test --release -p flaccy --bin flaccy real_video -- --ignored --nocapture` against YouTube, and the rig in `~/.cache/flaccy-precache-e2e/run.sh <bin> <secs> <track>` (copy of the mv-e2e library; the second run logs `playing the prepared file for …` and the first frame in 0.9 s). Measured sizes at 720p AV1: 20.8 and 25.5 MB for 3–4 minute videos.
- **Lyrics are fetched for the whole library in the background and a failing lrclib stays out of sight (2026-11-03), on every client.** Three layers, each mirrored. **Fill:** Linux `precache/lyrics_lane.rs` and Apple `Features/Lyrics/LyricsPrecache.swift` (an actor, started by `Library` loads and reloads and by the player's track and queue notifications, replanning 1.5 s after the last change) walk `lyrics_order` / `PrecachePlan.lyricsOrder` with the whole library on (queue first, then habit, new arrivals, the rest), one song at a time, local sidecars and tags included, so every song's lyrics are stored before it plays. The Linux switch `lyrics_whole_library` (Preferences, Prepare Ahead; **default on**, a new key because older builds wrote `precache_lyrics_library = false` as a default, not a choice) is the only way to turn it off; **Apple has no switch and always runs, a recorded gap** (lrclib already hears every played title). It pauses with no network and on a metered connection (Linux) or an expensive or Low Data Mode one (Apple), and never runs in a DEBUG screenshot launch, a scan bench or a test host. `DatabaseManager.songsWantingLyrics(revision:missesFetchedBefore:)` is the SQL twin of `is_current` (no row, a miss older than 30 days, content below the revision; `LyricsWantTests`); plays for the ranking come from `fetchListens()`. **Retry:** a song lrclib could not answer for goes into a `RetryLedger` / `PrecacheRetryLedger` and is asked about again when its pause ends (`retry_delay_seconds`: transient 30 s doubling to an hour, throttled 5 min to 6 h, blocked 30 min to a day, plus up to 30 % jitter); the lane shows "lrclib could not answer for N songs; resuming in …" meanwhile, and the `Breaker` / `LaneBreaker` (three hiccups, eight busy answers (`Failure::Busy`, an lrclib 503) with no song done between, or one refusal) rests the whole lane, so an outage costs about one request per rest, not thousands and a few songs lrclib has to think about do not hold up the ones behind them. A song counts as done only when its stored answer is current afterwards, so a lookup answered from an older row because lrclib failed is retried on the ledger instead of looping. The ledger is in memory: a restart tries every uncached song once more. **Every lrclib request on every client passes one gate** (450 ms apart, a 429 starts a cooldown of its full `Retry-After`; `LRCLIB` on Linux, `LyricsRequestGate` over `RequestGate` on Apple), so the panel and the lane cannot outrun a ban between them. **Silent foreground retries:** `next_retry` / `LyricsPatience.next` (3, 8, 20 and 45 s, shown once at the fifth failure, then every 60 s, never sooner than the gate's cooldown, a refusal (`Rejected`) shown at once and not retried) keep the panel on "Looking Up Lyrics…" for about 76 s; then it shows the failure and Try Again once and goes on asking every minute, replacing the message with the lyrics when they arrive. Linux: `lyrics::fetch_patient` (ends with its `stop` flag, the track no longer being the wanted one, or its channel closing), used by the panel and the seek bar's hover prefetch. Apple: `LyricsService.lyricsUpdates` (an `AsyncStream`) held by a `LyricsLoad` token in `LyricsViewController` and the Mac `LyricsPanelViewController`, so closing the view ends it. `LyricsService` is now `nonisolated` and `fetchLyrics` `@concurrent`: the cache, sidecar and tag reads of a whole-library fill no longer run on the main actor. The failure copy (`LyricsStatusCopy.failed`) is unchanged and still says to try again; it now appears only after the quiet window. **A busy lrclib is not a dead one.** lrclib answers `503 ServerOverloaded` after about half a second to any question it cannot serve from cache and goes on working on it, so the same question a moment later answers at once (probed 2026-11-03 with 33 songs: the exact lookup with album and duration succeeded for 8, the plain one for 14, search for 20, and asking the next question after a 503 resolves 23). The lookup therefore carries on to the next, plainer question after a 503 (`tries_next_question` / `LyricsPatience.triesNextQuestion`; `lookup_through` / `LyricsService.lookup`, tested with scripted answers on both sides) and counts as failed, never as a cached miss, when every question that did answer was empty; a timeout, no connection, a 429, a 500 or 502 or a refusal still ends it at once. A song lrclib does not have may answer 503 for its first one to three asks, some 12 s apart, before it answers a clean 404 (probed with the owner's own tracks), which is why a busy answer is retried soon and does not rest the lane. **Not built:** a persisted ledger, a background-processing task on iOS (the fill runs while the app is alive, which includes playing in the background), a Flaccy-run lyrics cache in front of lrclib (a flaccy-api route and a privacy decision), a switch on Apple. **Drill:** `FLACCY_LRCLIB_URL=http://127.0.0.1:<port>` points the Linux client at a stand-in server; the rig `~/.cache/flaccy-lyrics-lane-e2e/run.sh <binary> <seconds> <seconds the stand-in answers 503> <port>` runs a 33-song library whose durations are lrclib's own against a stand-in that fails for a minute and then relays to the real lrclib.

- **Music video mode is Linux-only, for the same reason Downloads is** (`linux/src/musicvideo/`, `linux/src/ui/video_view.rs`). It is always on since 2026-11-03 (no Video toggle; `musicvideo::start` enables it wherever `playbin3` exists, and the old `np_show_video` / `music_video_mode` keys are ignored): Now Playing is one stage for the song's music video, and the cover stands in its place until the first frame of this song (a stage state of Playing since the last load, so a previous song's last frame never shows) and for a song with none: a second `playbin3` decodes picture only into a `gtk4paintablesink` paintable while the lossless file on disk stays the clock. Seven pieces worth knowing before touching it. (1) **The pipeline flag `video+download` is load-bearing** — streamed straight from HTTP, playbin refuses every seek, and seeking is how the picture is held to the audio; with download buffering the measured drift goes from a permanent five seconds to ≤60 ms. With a GL sink (`glsinkbin` around the paintable sink, gst-plugin-gtk4 features `wayland`/`x11egl`/`dmabuf`) the flags add `native-video`, or playbin's software converters force every frame through system memory; the log line "decoder hands over … GTK paints …" says which path ran. (2) **Formats are chosen in Rust, not by a yt-dlp selector** (`stream::choose_format` over `--print formats`): plain HTTP only (YouTube's HLS variants need a transport-stream demuxer many installs lack), tallest under the ceiling first, then the codec this machine decodes cheapest — the registry is asked once which of AV1/VP9/H.264 have decoders playbin would plug and which are hardware (`stream::decodable_codecs`, `preference`); a decoder failure retries once with H.264 only. (3) **A freshly issued googlevideo URL can answer 403 for its first ~3 s** (yt-dlp ≥2026.10 resolves through the TV client), so the worker polls a one-byte range until it is served (`stream::await_ready`) and a pipeline 403 renews the URL once (`STREAM_REFUSED`). (4) **The video is not the album master** — runtime is bounded by *ratio* (0.5–1.9×), because official videos are routinely an edit of the album cut. Alignment is a whole-song *time map*, not one offset (`musicvideo::align`, `TimeMap` in `flaccy-library`): 10 s stretches of the local onset envelope are correlated against every position in the video's, peaks are linked into candidate lines (with a fitted rate, since vinyl rips run up to ~0.4 % off speed), and a Viterbi pass picks one line per stretch, paying to switch and only letting the video run backwards across stretches the earlier line could not hear — a dropped verse becomes a cut, a repeated chorus never pulls the picture to the wrong repeat. A map is trusted only when ≥60 % of the shorter recording finds its counterpart (real pairs: matches 0.68–1.0, a live take 0.36, a different recording 0.09). The stage seeks on each cut as the audio reaches it and holds the first frame while an album intro the edit dropped plays. Rows carry `alignVersion`; older alignments are redone once, and the listener's nudges live in `trimSeconds` apart from the automatic map. Run `FLACCY_ALIGN_PAIRS=<tsv> cargo test --release -p flaccy --bin flaccy real_pairs -- --ignored --nocapture` against real `local<TAB>video-audio` pairs before changing a threshold. (5) **Picking the right result is scored, not guessed** — uploader identity and view count carry it, because every re-upload copies the title; a local Ollama model only breaks ties the scorer calls close, and its verdict is blended rather than obeyed (`score.rs`, `llm.rs`). A track number in front of the title ("03 - Heartless", common in ripped discographies) is dropped before searching, and a bare-titled upload on the artist's own channel is treated as the label's still-image art track. Every decision row carries `matchVersion`; bump `worker::MATCH_VERSION` when the matcher changes and older misses and unchosen matches are decided once more (the same video keeps its alignment, nothing better keeps the old pick). Each song's outcome is logged (`matched …`, `no music video for …`, `rechecked …`). - **Equalizer audio-path rules that an independent review had to teach us.** (1) A kernel born with the beginning of a song starts *engaged* (`startsEngaged`, set by the engine for any item under 0.25 s in); one that appears under a song already playing fades in over 1 024 frames so enabling mid-song does not click. Fading in every new tap, as first written, glided each track's opening in from 0 dB over 23 ms. (2) The peak guard's ceiling is **full scale (1.0), not −1 dBFS**: at −1 dBFS it limited every hot master the moment the equalizer was switched on, with 4 % distortion on bass, and made Compare an unfair A/B. The guard keeps the stage out of bypass until it has released, so there is no gain step on hand-over. (3) Filter state and coefficients are double precision; float32 left −71 dBFS of arithmetic noise at 96 kHz and −64 at 192 kHz on a 28 Hz high-pass. (4) `Double("nan")` parses: every number read from profile text goes through `finiteNumber`, `EqualizerBand.clamped()` turns NaN into a usable band, and the kernel skips a band whose coefficients are not finite, because one NaN in the delay line silences the rest of the track. (5) The tap's kernel reference sits behind a lock (render threads only `withLockIfAvailable`), and spectrum demand is counted per screen (`beginAnalysis(for:)`), because a cancelled interactive dismissal calls `viewWillAppear` again without a `viewDidDisappear` and used to leave a tap attached forever. (6) Linux dithers 16-bit output, and only samples the stage changed, so a sample already on a step stays bit-exact. **Known gap:** `Headroom` and the graphic solver are computed at the 48 kHz reference rate while the kernel builds each biquad at the stream's real rate, so at 96 kHz a high band can land up to ~0.8 dB from the drawn curve and a +12 dB shelf at 16 kHz is attenuated ~2.5 dB too much (at 44.1 kHz the auto preamp is ~0.5 dB short and the guard catches it); fixing it means publishing per-rate variants of the resolved bands and preamp.

The ones that matter in music: Swift keeps `ø æ œ ł đ ı` and folds every other Latin Extended-A/B and Latin Extended Additional letter (Vietnamese included), Cyrillic `й ё ї`, and Greek tonos letters, so "Røyksopp" is `røyksopp` on iPhone and `royksopp` on Linux, and "Čechomor" (upper-case input is not lowered first in `artist_key`) is `cechomor` against `čechomor`. A song key is `SHA-256("fsk1" || artistKey || 0 || titleKey)` and clients send their own, so such songs get two keys once an iPhone and a Linux box share a Flaccy Server: loves, ratings and listens for them do not merge. Measured on the owner's own Linux library (2026-10-31), 23 of 7,873 distinct title, artist and album strings (0.3%) differ, almost all Nordic `ø æ` (Eivør, CASTRØ, Lux Æterna) and Cyrillic `й ё`. Changing it moves persisted keys (Linux `title_key`/`artist_key` columns and the registered `flaccy_norm`, and every songKey a Linux client already synced), so it needs a re-key migration, not a quiet edit (the Linux `scrobbles` table alone stores `titleKey`/`artistKey`/`albumKey` for 165,590 rows, and the server's `listens` store the same keys); the call, made with that 0.3% in view, is to change the Rust fold once, with the migration, in the release that ships Apple sync, not before: the cleanest rule is to make Rust fold exactly like Foundation (NFD, drop marks, plus the scalars Foundation maps itself) with the Swift dump as the golden vectors. Apple 1.14.0, the first Apple release with sync, was still unsubmitted on 2026-10-30, so the Apple side has no synced keys to migrate yet.
- **A scan lists music after the tags and fingerprints the rest in the background, in the Rust library and in the Swift scanner (2026-10-31).** `linux/library/src/scanner.rs` (the Linux client and `flaccy-server`) reads tags on eight threads and inserts rows in listing order, stores a file with no cheap fingerprint (everything but a FLAC whose STREAMINFO MD5 is set: MP3, Opus, WAV, M4A, and FLACs whose encoder left the MD5 zero) with no signature or fingerprint, and lets the revision pass behind the scan baseline it, which is the path rows from before versions existed already took. The server runs that pass in one-minute slices (`ScanOptions::revision_budget`, backlog in `ScanOptions::backlog`) and publishes the catalog while the tags are read, so a first scan of a slow volume lists everything in minutes instead of hashing every file first: measured on 7,412 files (6,832 FLAC) on an exFAT SD card, the old scan had indexed 2,350 in 27 minutes with no artist visible, the new one lists all of them in about 60 seconds with 2,769 files left to fingerprint at about 50 a minute from that card, so about an hour in the background. A re-export that lands before its file is baselined is taken as the baseline, which is the same trade the legacy rows already make. **The Swift side does the same** (`Library.swift` scan, `AudioFingerprinter.quickFingerprint(of:)`): a new file gets its signature and fingerprint at scan time only when its FLAC MD5 is set, and `LibrarySyncResult.indexedOnDisk` now carries every file on disk after a scan that added files, so the existing revision pass (`Library+Revisions.swift`, eight inspections at a time, already behind the reload) baselines the new rows. Proof: `Tests/flaccyTests/AudioFingerprinterTests` (run on the Mac in a scratch SwiftPM package around `AudioFingerprinter.swift`, `AudioPayload.swift` and `TrackRevision.swift`: 4 of 4 pass), a Debug build of `flaccyMac`, and the Mac app's own `--exercise-share-mac <folder> --skip-keychain` (it PASSED on 40 generated FLACs, the embedded server included; with the MD5 of every file zeroed the log shows "Revision pass: 40 baselined" and all 40 rows end with a `sha256:` fingerprint, size and modified time). `--exercise-reexport` was started the same way but stops at "the first version is indexed" in a throwaway `CFFIXED_USER_HOME`: the Mac app imports the old Mac app's handoff there, its bookmark does not resolve and the sync is skipped (`isFallbackActive`), which has nothing to do with the scan; run it on a real library root, and give a throwaway home a `Library/Caches` folder or `--exercise-share-mac` fails at its last step on `share-drive.json`.
- **Launch and idle on a large history (2026-11-20).** On the owner's iPad Pro (M1) with 599 albums, 12,706 songs and 165,806 plays the TestFlight log showed Home's first frame at 6.5–23 s and a Recap recompute of 1.6–4.5 s every few minutes while music played. Everything Home, Recap, the lyrics lane and the credit settling read goes through one `DatabaseQueue`, so whatever holds it holds Home. The rules that came out of it: **never decode the history row by row to count it** — `playTallies(since:countingArtists:)` folds per-song and per-artist counts in SQL (the mixes and the lyrics lane), `recentlyPlayedAlbums(limit:since:)` walks the live-timestamp index backwards and stops at the albums Home shows, `hasLivePlays()` asks for one row; **a screen nobody is looking at computes nothing** — Recap notes that it is behind and catches up in `viewIsAppearing` (`ChartsViewModel.setOnScreen`, iPhone, iPad and Mac); **`LibraryHygiene.primaryArtist` is memoized** (seventeen case-insensitive searches per call, 1.8 s of CPU at launch); and **the Now Playing backdrop holds still while the music is paused** (`setHoldsStill`; it drew at 28 fps all day beside the library), finishing a colour crossfade first and resuming its flow where it stopped. Measured by installing a development-signed Release build over the TestFlight one and recording `xctrace --template 'Time Profiler' --launch` on the iPad: Home's first frame 6.5–7.0 → 2.4–2.6 s, CPU in the first 40 s 13.5–14.2 → 5.9–6.3 s, idle CPU (Home and the column on screen, paused) 1.6 → 0.85–1.3 s per 20 s, the rest being artist enrichment.
- **A first scan lists songs as it reads them, can neither hang nor crash-loop on one file, and nothing rebuilds the library on the main thread (2026-10-31, after a 3-star review: "freezes, sometimes shows no songs, stuck at preparing your library").** Measured on the iPhone Air (Debug) with the owner's 7,599-song library plus 500 generated FLACs (`scripts/scan-bench/make-flac-library.py`, covers from none to a 3000 px PNG): first songs on screen 27.1 s → 3.6 s, worst main-thread stall during and after the scan 0.92–1.9 s → 0.26 s, peak memory 220 → ~155–200 MB; a relaunch of 8k songs restored in 1.05–1.77 s → 0.65 s with its 1.2–2.2 s stall gone (now 0.16–0.34 s). What changed, by cause: (1) **live listing** — a scan that starts from an empty library publishes the albums read so far through the ordinary `didUpdateNotification`, first after 3 s, then at most every 5 s (`FlaccyCore.LiveListingPace` ⇄ `linux/shared/src/live_listing.rs`, the same numbers and tests), which demotes the Debut to its sheet as soon as there is music; `Library.isListingPartial` is true meanwhile and anything that forgets a song because it is missing waits for the final load (`WatchSyncService.refreshRequestedFromLibrary`, `WantlistService.resolveAgainstLibrary`); a listing reads credits as stored and the final load settles them; Linux does the same in `AppCore::list_while_scanning` (its scanner rarely needs it: 7.7k files in 1.8 s from NVMe, but an SD card took a minute). (2) **One cover per album** — the database keeps one hoisted cover per album, so the scan asks `AudioMetadataReader.read(from:wantsArtwork:)` for a track's picture only while `ScanCoverLedger` says the album still lacks one, instead of decoding and re-encoding the same embedded image for every track (Linux already copies the raw bytes). (3) **A tag read cannot hang the scan** — `MetadataService.extractMetadata(from:within:wantsArtwork:)` gives each file 20 s (`FlaccyCore.Deadline`, which abandons rather than awaits a read that ignores cancellation), then files the song by its name and folders. (4) **A file that crashes the app is filed by name** — `ScanJournal` appends `R`/`S`/`D` lines beside the database (`FlaccyCore.ScanJournalReplay` reads them); the files in flight when a scan died are read again one at a time before the rest, and one that dies alone goes into `scan-quarantine.json` and is never opened again (the revision pass skips it too) while it stays on disk; the Rust scanner needs none of this, it catches a panicking file with `catch_unwind`. Verified by killing a scan mid-way on the phone: the 2,091 songs already read were back in 0.3 s, the 8 in flight were reread alone, the scan finished and the journal was gone. (5) **The main-thread freezes were `stat` calls and a full read**: `Track.fileURL(forStoredPath:)` asked `FileManager` for Documents and let `appendingPathComponent` stat the file, for every row of every load (`LibraryPaths.root` is now looked up once on iOS and the join passes `isDirectory: false`), and `LibraryViewModel.trackMeta` (date added, last played) was built from `fetchAllTracks()` inside `buildSnapshot` whenever a pivot or sort needed it — the owner keeps Albums on Recently Added, so every change froze the grid; `publishSnapshot` now awaits `warmTrackMeta()`, which builds it off the main actor. (6) **Credits on a settled library take no write lock** — Swift ports the Rust `has_covers_to_adopt` probe (one read decides there is nothing to do, so Home's first reads stop queueing behind a write on every launch), and both adoption statements skip releases whose credited row already has a cover before `MIN` reads a BLOB (120 ms → 5 ms on the owner's database copy). (7) `UNUserNotificationCenter.removePendingNotificationRequests` is a synchronous daemon round trip that held a fresh install's main thread for 8 s in the simulator; both schedulers go through `PendingNotifications.remove(withIdentifiers:)`, off the main actor. **Measuring it:** `--bench-scan` (iOS, DEBUG) parks the real `Application Support/flaccy` under `Library/ScanBench` and scans the real Documents into an empty database (`--bench-fresh` starts over, `--bench-poison` adds broken files; push a generated set to `Documents/Bench FLAC` with `devicectl device copy to`); any launch without the flag puts the real store back and removes both folders. It logs `SCAN BENCH` progress, the worst main-thread stall and database wait, a `RESULT` line, and `SCAN BENCH MAIN` lines from an in-process main-thread sampler, because Instruments often cannot attach to a phone over the network. `CFFIXED_USER_HOME` cannot isolate a device run: iOS overwrites it with the container path, and the container's path changes on every install.
- **The iPhone notices songs that arrive while the app is alive (2026-11-03).** The index used to be reconciled with the folder only at launch and after an import, so songs pushed over a cable, from the Files app or from a computer stayed out of Home and the Library until a relaunch (found after a `Music-AAC256` sync to the phone). `LibraryFolderPoller` (iOS only, started by `sceneDidBecomeActive`, stopped by `sceneDidEnterBackground` because music can keep the app running there) calls `Library.rescanIfFolderChanged(checkingVersions:)` at once and then every 30 s. It lists the folder and reads the stored paths without touching progress or notifications, so a pass that finds nothing is invisible (no banner, no Home rebuild); the first pass of each activation also runs the revision pass for songs replaced in place. Only a difference starts the ordinary `reload()`. Three guards, each load-bearing: a new file modified within 10 s of now (`settleInterval`, either direction, so a wrong-clock mtime in the future cannot hide a song) defers the whole pass, because indexing a copy still arriving stores a half-read song and the revision pass would later call the finished file a new mix; a difference that a reload did not settle (`unsettledFolderChange`) is not reloaded again until it changes, so one unreadable file cannot loop full scans every 30 s; and nothing runs before the first load has settled or while a reload is in flight. The Mac needs none of it (`FolderWatcher` is FSEvents over the library root) and Linux has its own rescan, so this is a platform-shaped difference, not a gap; the Mac target excludes the poller in `project.yml`. Compiled in Release for a device and in Debug for the Mac; not yet run on the phone: push a track with `sync-iphone.py` while the app is in the foreground and in the background and watch for `Library folder changed while running` in `flaccy.log`.

- **Downloads from a server can be AAC (2026-11-20), on iPhone, iPad, Mac and Linux; the watch is a recorded gap (it never downloads from a server itself).** Download Quality (`RemoteDownloadQuality` in FlaccyCore ⇄ `linux/shared/src/remote/download_quality.rs`, tests both sides): Original File, AAC 256 kbps (default, what AirPods receive over Bluetooth) or AAC 128 kbps; iOS Settings › Servers › Server Cache, the Mac's Servers pane, Linux Preferences › Servers › Cache (`remote_download_quality` in `config.toml`), Apple `flaccy.remote.downloadQuality`. A Flaccy Server is asked for `stream?format=mp4&maxBitRate=…`, every other server for `format=aac`; the response's media type names the file (`m4a`/`aac`), and anything else (or a Subsonic error) falls back to downloading the original. The conversion is stored as the song's kept file with `conversion` in its sidecar, so playback, lyrics, artwork and the watch relay read it unchanged. **Gapless:** only a finished mp4 carries the edit list that trims the AAC encoder's 1024 priming frames, so Flaccy Server writes `format=mp4` whole (`-movflags +faststart`) before sending it; the old fragmented output made AVFoundation assume 2112 priming and cut 25 ms of music off each song. AVFoundation decodes the whole m4a to the exact sample count (882000 for 20 s at 44.1 kHz) even though `AVURLAsset.duration` reports 25 ms short, so check decoded length (`AVAudioFile.length`), never the asset duration. ADTS from other servers has no such trim (recorded). Proof: `--exercise-remote` downloads a song in AAC, checks it is smaller, decodes to the song's exact length and plays, then replaces it with the original; Linux `a_download_in_aac_keeps_the_servers_conversion_and_the_original_quality_keeps_the_file`; server `ffmpeg_converts_to_the_format_asked_for` checks the mp4 has `moov` before `mdat` and an `elst`. Rig used: a local `flaccy-server` on the Mac over a pink-noise FLAC album (sine tones compress below AAC sizes and fail the size check).

## iPad

Flaccy for iOS is universal (`TARGETED_DEVICE_FAMILY: "1,2"`); the iPad runs the iPhone's code with an iPad layer in `App/Pad/` (all excluded from `flaccyMac`). The iPhone and the iPhone Duo are unchanged by it apart from Home's wide threshold (below), the keyboard shortcuts and positional queue moves.

- **Sidebar (`PadSidebar`).** `AppTabBarController.configurePadTabs()` sets `mode = .tabSidebar` on an iPad: Home, the Library group (Albums, Songs, Artists, Playlists as pivots managed by `libraryNavigation`; every pivot shows the one `LibraryViewController`, `displayedViewControllersFor` returns `[library]` and selection drives `select(segment:)`), Recap, Search, then the sidebar-only Playlists section (one tab per playlist from `DatabaseManager.observePlaylists`, a GRDB observation, plus New Playlist) and Discover (Wantlist, Listening Guide, Year in Music as an action). While the sidebar is available and shown the Library hides its segmented picker and titles the bar with the pivot (`setSegmentPickerHidden`). Three UIKit traps: every root `UITab`, groups included, must own a view controller or `setTabs` asserts (sections hand over `SidebarSectionPlaceholder`); setting `mode` loads the tab controller's view, so callbacks are wired in `configurePadTabs` before it; and in a compact window the tab bar lists sidebar-only groups anyway and pushes Search behind More, so `fitSectionsToSidebar` swaps the root tabs to the iPhone's four whenever the sidebar is unavailable and back when it returns.
- **The sidebar floats.** On iPadOS 26+ it is a glass panel that docks (content inset through the safe area) only when the tab controller is wide, and slides over dimmed content otherwise; `preferredLayout = .tile` changes nothing there, so it is left automatic. That is why the Now Playing column does not narrow the tabs.
- **Now Playing column.** `AdaptiveLayout.SplitStyle(division:)` is `.column` for any window no fold runs down, which on a real device means an iPad: once something is playing and the window leaves the library `columnLibraryMinimumWidth` (760 pt) beside `playerColumnWidth` (30% of the window, 360-440 pt), `RootContainerViewController` lays the player over the trailing edge and gives the tabs `additionalSafeAreaInsets.right` instead of a narrower frame, so the sidebar still docks (13" and 11" landscape, mini landscape; never portrait). It slides in on the first song and out when the queue empties or the person hides it (`PlayerColumnSetting`, View > Now Playing Column, ⌥⌘0). The pane rounds only the window's corners, tightens its margins and control spacing, lets the cover shrink before the controls (`fitColumnPane`) and lists Up Next under the title when 150 pt are left (`QueueViewController.listsUpNextOnly`). Lyrics and the queue open inside the column, as they do in the iPhone's player, so the library stays beside them (only halves at a fold spread for them, `AdaptiveLayout.centerStateSpreadsPane`); spreading the column over the window is the person's choice, from the glass expand button beside its hide button or ⇧⌘F, and its button, ⇧⌘F or Escape (View > Back to the Column, a menu command so it never takes the keyboard from a text field) bring it back (`requestColumnSpread`); a column put away or a queue that runs out while it is spread leaves from beside the library and ends as the mini player (`leaveSpread`, `compactKeepsPlayerExpanded`); a spread player showing its cover takes the whole-window layout, lyrics or the queue the focus pages (`usesFocusArrangement`), and anything that navigates (an artist or album name, ⌘1–⌘6, ⌘F) brings the column back first. The paths and the reasoning are in `docs/ipad-now-playing.md`; `--exercise-column` walks it on a real iPad's own queue with no touch and no seeded data (`COLUMN EXERCISE PASSED`). A fold, if one were ever reported, still decides where either style splits.
- **An iPad mini on its side: the sidebar and the column take turns.** Held sideways the mini is 1158 x 756, and a docked sidebar (280 pt) with the column (360 pt) left the library about 520 pt between them: Home stacked, the album wall cramped, three busy panes. `AdaptiveLayout.columnFitsBesideSidebar` asks for 540 pt of library beside a docked sidebar (an 11-inch keeps 567 and is unchanged; a 13-inch keeps more); below that `RootContainerViewController` lets the one the person brought out last have the room (`SideTurn`). By default the sidebar has it, Home goes wide beside it and the mini player carries playback; asking for the column (a long press on the mini player, View > Now Playing Column, ⌥⌘0) hides the sidebar and slides the column in; bringing the sidebar out (its toggle in the floating tab bar, or View > Show Sidebar) sends the column back to the mini player; putting the column away (its button, the queue running out) brings back a sidebar that stepped back for it. The docked width is read from the tabs' content inset (`dockedSidebarWidth`) once the sidebar's animation completes (`PadSidebar.onSidebarVisibilityChange`). The column's turn holds through a resize (`keepColumnTurnFitting`): a window that narrows until the docked sidebar would leave the library short of 540 pt beside the column has the sidebar step back then too; and a stepped-back sidebar comes back whenever the column goes, including a column put away while it is still sliding in (`viewDidLayoutSubviews` returns it as the split ends, where the hide that `refreshColumn` held off used to leave it hidden). DEBUG: `FLACCY_COLUMN=1`, `FLACCY_SIDEBAR_LATER=1` and `FLACCY_HIDE_COLUMN_LATER=1` (or a delay in seconds after the column's turn, `0.1` to hide it mid-slide) drive the three moves after a route, because synthetic AXe taps do not reach the `UIRequiresFullScreen` copy on a landscape screen.
- **The whole-window player** caps its single column at 640 pt and puts the cover beside the controls on a window at least 1000 pt wide and wider than tall, and (no fold reported, so never the Duo) on any window at least 720 pt wide and 0.9 as wide as tall whose cover beside the controls comes out at least as large as above them (`sideBySideCover` >= `portraitCover`): two thirds of a landscape iPad (~800 x 834, 376 pt beside against 350 above) and the top half of a portrait one (834 x 600) used to shrink the cover to a thumbnail above stretched controls, while 720 x 800 keeps the single column (296 pt beside would lose to 336 above) (`AdaptiveLayout.playerLayout(hasFold:)`). How the width divides is `AdaptiveLayout.landscapeSplit`: a short window (560 pt tall or less: a phone on its side, a short Stage Manager window) keeps the phone's proportions, the centre 36% of the safe width for the cover and 50% for lyrics or the queue with the controls beside it; anything taller gives the controls a column against the edge the thumb reaches, 440 pt where the height limits the cover anyway and narrowing to 340 pt so a squarish window keeps its cover (`playerSideControlsWidth(size:)`, at most 60% of the window, its constant updated in place while a resize keeps the window side by side), and the cover, lyrics or queue take the rest, so on a whole landscape iPad play and skip sit within a thumb's reach of the right edge instead of mid-screen. Held upright on an iPad with no fold (a mini included), the single column's cover may take 58% of the player's height instead of 42% (`portraitArtworkShare`), so the tall screen goes to the cover rather than to gaps above and below the title; a phone and a Duo keep 42%.
- **Controls go to the hand (iPad).** Held in both hands, the thumb that reaches a window sharing the screen is the one on the screen edge it lies against (within 48 pt, `AdaptiveLayout.outerSide`). The mini player puts queue, play and next at that end (artwork and title at the other; leading when the window spans the screen or floats, as on the iPhone), and the landscape player puts its controls column there (trailing otherwise), `controlsSide`. iPadOS tells an app nothing when its window only moves (no layout, no `effectiveGeometry` change, no `didUpdateEffectiveGeometry`; measured on 27.3), so the side is read on every layout pass, when the scene activates and with each 0.25 s playback-progress tick; the morph reads `MiniPlayerView.artworkIsOnRight` so the flying cover leaves from the right end.
- **The column by touch.** A glass `sidebar.trailing` button in the column's top corner hides it (the same setting as ⌥⌘0), and a long press on the mini player offers Now Playing Column back whenever the window has room for it (`AppTabBarController`'s context menu).
- **Resizes keep what is open.** UIKit asks `displayedViewControllersFor` again for the pivot already showing whenever the window crosses between a sidebar and a tab bar; answering with the Library root alone closed an open album, artist or playlist on every Split View drag past the compact width. `PadSidebar` now keeps the stack for the pivot it last displayed and starts a different pivot from the root. `RootContainerViewController` logs `Window resized to WxH, drawn after N ms` (performance): while that runs iPadOS shows the previous frame stretched or squeezed into the new tile, which is the "crushed" look; the simulator measures 14-19 ms per step with the seeded library.
- **Home** goes wide (hero beside Jump Back In) from 760 pt of content, not 600, so the tiles keep whole words; the iPhone Duo's inner portrait (669 pt) now uses the stacked Home. Under a stacked hero, Jump Back In lays three tiles across from 700 pt of content (`homeJumpColumns`), so an upright mini (756 pt) shows its six tiles in two rows instead of two half-page columns; phones and the Duo's inner portrait (669 pt) keep two.
- **Menu bar and keyboard (`AppCommands`, `AppCommandTarget`)** mirror the Mac's menus: Settings ⌘, ; Import Files ⌘O, New Playlist ⌘N; Find ⌘F; Home ⌘1, Albums ⌘2, Songs ⌘3, Artists ⌘4, Playlists ⌘5, Recap ⌘6; Toggle Queue ⌘K, Toggle Lyrics ⇧⌘L, Now Playing ⇧⌘F, Now Playing Column ⌥⌘0; Play/Pause Space, Next/Previous ⌘→/⌘←, Toggle Shuffle, Cycle Repeat Mode, Love Track ⌘L, Equalizer ⌥⌘E, Song Volume…, Song Louder/Quieter ⇧⌘↑/⇧⌘↓. Every item lands on `AppDelegate` (the end of the responder chain), is dimmed when it means nothing and checked when it is on; navigation waits while a sheet is up. A hardware keyboard on an iPhone gets the same shortcuts. `UIMainMenuSystem` keeps the sidebar toggle and drops document, printing, find, toolbar, inspector and new-window groups.
- **A list that takes drops must hand its own grabber reorder back.** An iPad routes an editing table's grabber drag through the table's drop delegate; a delegate that only accepts songs from elsewhere cancels it and the row never moves. Up Next (`QueueViewController`) and a playlist in Edit (`PlaylistDetailViewController`) answer `tableView.hasActiveDrag` with `canHandle` true and a `.move`/`.insertAtDestinationIndexPath` proposal, which makes UIKit call `moveRowAt`, and ignore it in `performDropWith`. `PadPlayerUITests` drags a grabber in both (XCUITest `press(forDuration:thenDragTo:)` works where AXe drags do not).
- **Drag and drop (`TrackDrag`, `AudioFileDrop`).** Library tiles (album, song, artist), album rows and playlist rows drag their songs; a single local song also carries its file out to other apps. Drops land in Up Next where they fall (`insertInUpNext`, unit-tested), at the end of a sidebar playlist or of an open playlist. Audio files dropped on the window from other apps are kept as hard links (a copy only when linking fails and the file fits), then imported through `LibraryViewController.importFiles(at:reportingIn:)`, the Files picker's path. Drag sources and the playlist drop target are installed on an iPad only, because a list drags by default on an iPhone too and would arm a drag beside every context menu there. Queue moves in `PlaybackEngine.moveInQueue` track the playing song by position (`index(of:afterMovingFrom:to:)`), as Linux's `move_queue_entry` does, so a song queued twice never moves the playhead.
- **Pointer**: covers lift and rows highlight under the pointer (`liftsUnderPointer`, `highlightsUnderPointer`).
- **Popovers**: an iPad refuses an action sheet or share sheet without an anchor; every one now goes through `anchorPopover(at:fallback:)` or a bar button item.

## Key Technical Details
- **Database**: GRDB (SQLite) for library persistence, metadata, scrobble queue
- **AI**: Claude Haiku 5.5 via the flaccy-api proxy Worker (guitaripod/flaccy-api, flaccy-api.midgarcorp.cc, secret `ANTHROPIC_API_KEY`) for music identification and metadata cleanup — no API key in the app. The shipped clients still speak the OpenAI chat-completions shape and still name `GroqService` and a llama model they never read; the Worker alone translates to the Messages API and picks the model, so a model swap needs no app release. Deliberately not routed through mako: it meters per-user credits behind a tenant and wallet, while Flaccy's AI is bundled with the entitlement and keyed only by anonymous device and IP quotas in the Worker. A request that fails on our side (upstream 429/5xx, which includes a missing or revoked key) is **refunded** against those quotas (`RateLimiter.refund`): before that, the day Groq withdrew its model every failed call still counted, and the Mac's whole 150-request device allowance was gone by noon, locking AI out until 00:00 UTC. The allowances and the day's dollar ceiling have one home, `services/flaccy/README.md` ("Allowances"); one cleanup request is one folder's batch. Since 2026-11-20 they are two lanes: until then one allowance of 250 calls a network held every model call, so a library of more than 250 folders spent its network's day minutes after each UTC midnight and Make a Playlist, the described equalizer and lyric meanings answered that the allowance was used up for as many days as the cleanup lasted, which for a large library was the whole trial. Library cleanup is now counted apart from what a person asks for, and a device's cleanup past its first 100 calls of a day stops at 70% of the day's dollars, so one enormous library cannot spend the day for a newcomer's first folders or for anyone's asks. Deploy the Worker with `npx wrangler@4.149.0 deploy` — the version pinned in the repo fails against Cloudflare's current API.
- **Scrobbling**: Last.fm API with ASWebAuthenticationSession OAuth. **The Last.fm shared secret lives only in the flaccy-api Worker** (`LASTFM_SECRET`, set with `wrangler secret put`): every signed call (`auth.getToken`, `auth.getSession`, `track.scrobble`, `track.updateNowPlaying`, `track.love`, `track.unlove`) asks `POST /v1/lastfm/sign` for its `api_sig` with the same `X-Device-ID` the AI route uses (`LastFMService.requestSignature`, `linux/src/lastfm.rs`), and read-only methods stay unsigned. Signing counts against the same per-device/IP/global quotas as AI. Session keys stay on device. - **Target**: iOS 18, iPhone and iPad (one universal app; see "iPad" below)

## Flaccy Server on the local network (2026-11-13)

- **What it is.** `lan = true` (Linux server config; the Mac's Share this Mac's library sets it unless "Devices on this Wi-Fi connect directly" is off) binds the private addresses of the host's real interfaces next to the tailnet ones and serves local network peers TLS with a self-signed P-256 certificate issued at every start for one key, `lan-key.der` (0600) in the data folder (`linux/server/src/lan_identity.rs`, `net/lan.rs`, `net/serve.rs` does the handshake in the connection task with a 10 s deadline). Tailnet and loopback stay plain HTTP on the same port; the TLS decision is the peer's address class (`lan::wants_tls`). Devices pin the SHA-256 of the key's uncompressed point (`CertificatePin` in FlaccyCore and `remote/certificate_pin.rs`, same vectors in both test suites), never a CA: `PinnedServerTrust` (URLSession delegate, every Flaccy Server session, the Subsonic client and its stream session, the live socket) and `remote/pinned_tls.rs` (rustls verifier for ureq and tungstenite). A refused key cancels the challenge; Apple reports `URLError.cancelled` for that, so callers ask `refusedKey(explaining:)` (true only when the last handshake was refused and the task ended as a refused challenge ends, so a server that is later simply off reads as offline) and throw `keyChanged` instead of a silent cancel. An `https` address typed by hand on the local network is trusted on first contact (`ServerKeyTrust.firstContact`, `Transport::first_contact`), only for the first key it shows (later handshakes of that client, a redirect to another host included, must show the same key), and pinned at enrollment; any other `https` address keeps the system's CAs on both clients.
- **Links and storage.** The link carries `pin` and one or more `alt`s (PROTOCOL.md 3.4, `reach.rs` picks them): with Tailscale up, `url` is the tailnet address and the Bonjour name and the IP follow as two `alt`s, since a phone off the tailnet may not resolve `.local` (arch has no nss-mdns); local network only, `url` is the Bonjour name and the IP is the `alt`. Engines try `url`, then each `alt` in order only when the one before is unreachable, and store the address that answered with the pin: Apple `sync_meta.server_pin`, `remoteServers.certificatePin` (migration v23) and `ServerSyncServer.pin`; Linux `sync_meta` `server_pin` and `servers.toml` `pin`. `ServerSetupFlow.connect` takes the scanned link's pin and fallback (it used to rebuild the link from the address alone).
- **Traps found while building it.** avahi renames a clashing host (`arch` became `arch-2.local` here), so the link's name comes from avahi itself over D-Bus (`busctl ... GetHostNameFqdn`) or the Mac's `scutil --get LocalHostName` / `SCDynamicStoreCopyLocalHostName`, never from the host name; with no Bonjour name the link uses the IP. Docker bridges (`docker0`, `br-*`) are private addresses: they are skipped by interface name and the default-route interface goes first, or the link named 172.17.0.1. The iPhone simulator could not reach `arch-2.local` (5 s timeout) although the Mac resolves it in 24 ms; the link's IP fallback carried it, so a real device may store either. Against a server on the Mac itself the simulator fails `<mac>.local` in 0.5 s: macOS resolves its own Bonjour name to loopback, bridge and link-local addresses as well, and a loopback peer is served plain HTTP, so the TLS handshake fails and the IP `alt` connects; a real iPhone never resolves it to the Mac's loopback. The first local network connection on iOS raises the Local Network alert and fails while it is up, so the setup guide and Add Flaccy Server ask early by browsing `_flaccy._tcp` (`LocalNetworkAccess`, NSBonjourServices on iPhone and Mac); not yet watched on a real iPhone.
- **Verified.** `cargo test --workspace` (server, library, client), `server/tests/lan.rs` (enroll, sync and the live channel over pinned TLS on this machine's real LAN address; a wrong pin is `KeyChanged`, plain HTTP is refused, first contact learns the pin), FlaccyCore/FlaccyEngine/FlaccyServerEmbed tests on the Mac, and `--exercise-server` in an iPhone simulator against a Linux server sharing on arch's LAN and against a Mac server with a local-network-only link (`SERVER EXERCISE PASSED` both, pinned, live channel open), a Linux client on arch enrolling with the Mac server's links (Tailscale and local network only: `.local` fails on arch, the IP connects, a wrong pin is `KeyChanged`, plain HTTP is refused), and a 15-minute `server-soak.sh` with 4 clients (PASS). A Mac server for cross-machine checks has to run from a path the Application Firewall already allows (stealth mode accepts the TCP connection of a new unsigned binary and never delivers its data). Rig: a throwaway config with `lan = true` in `~/.cache/flaccy-nux-e2e`, `flaccy-server enroll --json`, a link with `url=https://<name>.local:<port>`, `pin` and `alt=https://<ip>:<port>`, passed as `FLACCY_EXERCISE_SERVER=<the whole link>` (the exercise now takes a link as well as `url|code`).
- **Review (2026-11-13), known gaps left open.** An adversarial review of the LAN and first-run commits found the fixes now on master (first contact only on the local network and only for the first key, `refusedKey(explaining:)`, the leaked stream session, setup's duplicate `lan` key, `Config::shares_on_local_network`, VPN interface names, the key race, link and IP literal parity, Linux scan failures and replayed rescans, Wi-Fi Transfer's stale card, the Mac join key, the watch plurals). Left as they are: (1) a 100.64/10 address on a real interface counts as tailnet, because tailnet detection is by address (it predates LAN sharing), so a Wi-Fi that hands out CGNAT addresses is served plain HTTP; telling them apart by Tailscale's interface breaks when `tailscaled --tun` renames it. (2) A typed address makes two first contacts, the probe and the enrollment, on both clients alike; carrying the probe's key into enrollment would narrow the trust-on-first-use window to one handshake. (3) Linux's live channel retries a refused key like an offline server (the sync poll shows the key change). (4) Older setup copy differs: Linux's generic failure names `flaccy-server doctor`, a 403 at the probe reads "isn't a Flaccy Server" on Linux and generic on Apple, and Linux checks the `sync` feature before the protocol. (5) A hand-made link without scheme or port normalizes differently (Linux `https` without 4545, Apple 4545 and the scheme by locality); links the server makes always carry both. (6) A device keeps only the address that answered at enrollment; the link's other addresses are not kept. In the iPhone simulator `arch-2.local` resolves at one moment and not the next (enrollment over it succeeded, then every sync round timed out with no connection reaching the server, while the same build passed over the IPv4 and the IPv6 literal and the Mac host resolved the name in 10 ms every time), so a phone that enrolled over the Bonjour name has no way back to the IP if `.local` later fails. The fix is to keep the alternates next to the pin (`sync_meta`, plus the Flaccy Server's `remoteServers` row for streaming, which needs a migration, and the Keychain token, which is keyed by the server URL) and fail over to them in the transports; wait for a real iPhone on TestFlight to show whether `.local` is flaky outside the simulator.

## Moving songs on this device to a server (Apple engine, 2026-11-20)

- **Pairing.** `ServerMovePlan` (FlaccyCore, mirrored in `linux/shared/src/remote/server_move.rs`) pairs local rows with a server's rows by sync song key, then the same audio fingerprint, the same album key within 2 s, or the same track number within 1 s on another album; one local song per server song, the copy the person uses most (on the watch, loved, played) as the pair, ahead of the closest length, further copies as duplicates. On an iPhone with 8,431 local AAC transcodes against a 13,823-song FLAC server it paired 6,797 and found 87 duplicates in 34 ms; 1,535 of the 1,547 left are songs the server does not have. Fingerprints never match a transcode (`flac:` against `sha256:`), so metadata carries almost every pair.
- **The database step** (`DatabaseManager+ServerMove.swift`, migration v24 `serverMoves`) turns the local row into the server's row in place, so the id (plays by id, `sync_song_keys`), love, play count, dateAdded and artwork stay; the server's own row is deleted first because `fileURL` is unique, playlist places move to the server path, lyrics and their offset are copied to the server's spelling, and a custom cover follows a renamed album. Loves merge as OR, plays as max for a pair and as a sum for a duplicate. A pair whose love the server lacks returns `starOnServer`, sent as a Subsonic star; `RemoteCatalogSync.playStates` lets an unsent star wish win over the catalog, which also fixes a love made offline being undone by the next sync.
- **The file step** (`ServerMoveFiles`) reads the journal: a kept song becomes the server song's download through `RemoteStreamCache.adoptDeviceCopy` (sidecar `conversion = "device"`, moved on iOS, copied then trashed on the Mac); any other file is deleted (Trash on the Mac) and emptied folders are pruned. A file the player has open waits for the next track change. `Library.audioPathsOnDisk` skips journaled files and every reload finishes pending ones first, so a crash between the two steps neither loses the song nor lists it twice; a journaled song whose server row is gone keeps its file and is listed again.
- **What follows a move.** `ServerMoveService.didMove` is posted before the library reload so `WatchSyncService.formerWatchPath` keeps the moved song's old watch stem (the copy on the watch stays the same song); `PlaybackEngine.replaceTracks` swaps queued tracks and keeps the item already playing.
- **Offer timing.** `RemoteCatalogSync.firstSyncDidFinish` triggers the one-time offer (`ServerMoveOfferLedger`), which waits while `ServerMergeReporter.isAhead`. The merge summary now counts loves by song key, so a song held twice (its own file and the server's copy) is one new love, as Linux already counted.
- **Verify.** `swift test` (ServerMovePlanTests, ServerMoveDatabaseTests, ServerSyncMergeTests), `cargo test -p flaccy-shared server_move`, and `--exercise-server-move` (iPhone simulator, `FLACCY_EXERCISE_SERVER=<link>`, Documents seeded with `MoveExercise/`: AAC copies of three server songs with the server's tags, a second copy in `Copy/`, and `Only Here.m4a`) logs `SERVER MOVE EXERCISE PASSED`. Pictures: `--shot-flaccy-server move-offer|move-done|detail` (iPhone, iPad) and `--shot-server-move` (Mac: captures the offer, the server sheet and the result as `flaccy-shot-server-move-*.png` in the temporary folder). Both drills run on the Mac too: launch the unsigned build's binary with `CFFIXED_USER_HOME=<throwaway home>` holding `Library/Application Support/flaccy/Music/MoveExercise`, `--skip-keychain`, `--handoff-container <empty folder>` (else a stale export of the old Mac app is imported and the folder is treated as offline) and `-flaccy.mac.shareLibrary NO -flaccy.mac.libraryBookmark ""`; trashed test files land in the real `~/.Trash`. A throwaway server on the Mac must be reached on 127.0.0.1 (stealth mode drops an unsigned server on the tailnet address); `enroll --url http://127.0.0.1:<port>` makes the link.

## Flaccy Server sync (Apple engine)
- **Layers.** Pure wire models, the transport protocols, `SyncStatus`, `FlaccyServerLink` and the scalar rules are in `Core/FlaccyCore/Sources/FlaccyCore/ServerSync/` (the watch never links the rest). GRDB state, recorder, engine and materializer are in `Core/FlaccyCore/Sources/FlaccyEngine/ServerSync/` and fold with the Rust core through the `FlaccyServerCore` package (`ServerCoreBridge`). The URLSession client is `App/Network/FlaccyServerClient.swift`; the token lives in `RemoteCredentialStore` (`ServerTokenStore`). The reference algorithm is `linux/server-core/src/sim/client.rs`; the Linux client's `linux/library/src/server_sync/` is the same design in Rust.
- **Recording.** `DatabaseManager` write methods call `ServerSyncRecorder` inside their own transaction (`playlist` create, rename, delete, cover, tracks added, removed, moved; loves; plays; lyric offsets). `ServerSyncGate` is the cached flag that makes it free with no server. File-vanish deletions (library scan) and hygiene merges are deliberately not synced; Wantlist, Tracks and Remote server rows are not synced yet.
- **Tables (migration v19).** `sync_meta`, `sync_base` (with `parent` for entries), `sync_pending` (with `sent`, so a push in flight is never coalesced into), `sync_ghosts`, `sync_blobs` (cover images, kept so a cleared cover is told from one the server never had), `sync_song_keys` (song key per track), plus `syncId` on `playlists` and `playlistTracks` and `eventId`, `suppressed` on `scrobbles`. Every Stats query filters `suppressed = 0`.
- **Rules that break things.** A mutation leaves `sync_pending` only when a pull with `more = false` reports `lastMutationId >= id` for an acknowledged one. A push answer only acknowledges (or marks failed). `Disconnect` keeps `syncId`s and `eventId`s so reconnecting to the same server finds its playlists instead of creating them twice. Ids of pre-sync playlists, entries and migrated plays come from `ServerCore` only. A `ServerJSON` is never `ExpressibleByNilLiteral`: use `.null`.
- **Testing.** `swift test` in `Core/FlaccyCore` on the Mac runs `Tests/FlaccyEngineTests/ServerSync` against `FakeFlaccyServer` (the real Rust apply code behind a fake transport); the pure wire, link and status tests also run on Linux. `--exercise-server` with `FLACCY_EXERCISE_SERVER=<url>|<code>` drives a real server from a throwaway database and logs `SERVER EXERCISE PASSED`.
